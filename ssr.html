dns

什么是 SSR？

Server-Side Rendering（服务端渲染）是指在服务器上将 React/Vue 等组件渲染为完整的 HTML 字符串，然后发送给浏览器，浏览器拿到 HTML 后即可立即展示页面内容，再由前端 JS 接管交互（Hydration）。

lightbulb
核心价值：首屏性能（FCP/LCP）+ SEO 友好。搜索引擎爬虫和用户都能第一时间拿到完整内容，而不是一个空白的 <div id="root">。
difference

SSR vs CSR 关键区别

🖥️ CSR（客户端渲染）

  • 服务器返回空 HTML + JS bundle
  • 浏览器下载、解析、执行 JS
  • JS 执行后才渲染 UI → 白屏时间长
  • SEO 不友好（爬虫看到空壳）
  • TTFB 快，但 FCP/TTI 慢

🌐 SSR（服务端渲染）

  • 服务器返回完整 HTML
  • 浏览器立即可见内容 → FCP 快
  • Hydration 后可交互 → TTI 稍有延迟
  • SEO 友好（爬虫拿到完整内容）
  • TTFB 可能稍慢，但总体体验更优
category

Hydration（注水）机制

SSR 返回的 HTML 是静态的——没有事件监听、没有状态管理。Hydration 就是让客户端 JS 在已有的 DOM 上"附着"事件和状态，使其变得可交互。

import { hydrateRoot } from 'react-dom/client';

// 不是 createRoot，而是 hydrateRoot
hydrateRoot(
  document.getElementById('root'),
  <App />
);
warning
Hydration Mismatch：服务端和客户端渲染结果不一致时，React 会报错并尝试修复。常见原因：访问 window/document、随机值、时间格式化。

SSR 涉及的关键模块

html renderToString

同步将 React 组件树渲染为 HTML 字符串。简单但不能流式输出。

water_drop renderToPipeableStream

React 18+ 流式 API，支持 Suspense 降级，逐步发送 HTML，TTFB 更快。

data_object serialize

将服务端获取的数据序列化注入 HTML，客户端通过 __NEXT_DATA__ 等机制读取，避免重复请求。

security CSP / Trusted Types

内容安全策略防止 XSS。SSR 场景需要特别处理 inline script 的信任类型。

route

SSR 完整请求生命周期

1

浏览器发起请求

用户访问 https://example.com/about，浏览器发送 HTTP GET 请求到 Node.js 服务器。

2

服务端路由匹配 & 数据获取

服务器匹配路由，执行 getServerSideProps（Next.js）或 loader（Remix），从数据库 / API 获取页面所需数据。

3

渲染组件为 HTML

用 renderToString 或 renderToPipeableStream 将 React 组件树 + 数据渲染为 HTML。

4

拼装完整 HTML 文档

将渲染好的 HTML、序列化的数据（JSON）、JS bundle 的 <script> 标签拼装成完整文档返回。

5

浏览器解析 & 绘制

浏览器解析 HTML → 构建 DOM → 首次绘制（FCP）。用户此时已可见页面内容。

6

JS 下载 & Hydration

浏览器下载 JS bundle，执行 hydrateRoot()，在已有 DOM 上绑定事件、恢复状态 → 页面变为可交互（TTI）。

stream

React 18 流式 SSR（Streaming SSR）

传统 SSR 必须等所有数据都拿到后才能开始发送 HTML。React 18 的 renderToPipeableStream 配合 <Suspense> 实现了渐进式发送：

import { renderToPipeableStream } from 'react-dom/server';

app.get('/*', (req, res) => {
  const { pipe } = renderToPipeableStream(
    <App url={req.url} />,
    {
      onShellReady() {
        // Shell（非 Suspense 区域）就绪，立即开始流式输出
        res.setHeader('content-type', 'text/html');
        pipe(res);
      },
      onShellError(err) {
        // Shell 渲染失败，降级为 CSR
        res.status(500).send('<div id="root"></div>');
      },
      onError(err) {
        console.error(err); // 流中某块出错，不中断整个流
      },
    }
  );
});
lightbulb
Suspense 边界内的慢数据会延迟渲染，外层 Shell 先到达浏览器。用户先看到骨架，数据到了再"弹出"内容 → TTFB 大幅降低。

Hydration 常见陷阱

  • 访问浏览器 API：window.innerWidth、localStorage 等在服务端不存在，需用 useEffect 或 typeof window 守卫
  • 随机数 / 时间：Math.random()、Date.now() 服务端和客户端结果不同 → 用固定 seed 或延迟到客户端
  • 浏览器扩展注入 DOM：Grammarly 等扩展修改了 DOM 结构，导致 React 比对失败
  • 嵌套 <html> / <body>：React SSR 要求组件树不包含这些标签（框架处理）
  • CSS-in-JS 顺序：服务端和客户端样式注入顺序不一致会导致闪烁
speed

1. 数据获取优化

  • 并行请求：多个 getServerSideProps 依赖的数据用 Promise.all 并行获取，不要串行 await
  • 只传必要数据：不要把整个数据库对象传给客户端，只序列化页面需要的字段
  • Edge Runtime：将数据获取逻辑部署到边缘节点，减少服务器到数据源的延迟
  • 请求去重：React 18 自动去重同一 render 中的重复 fetch，但自定义 client 要手动实现
// ✅ 并行获取
export async function getServerSideProps(ctx) {
  const [user, posts] = await Promise.all([
    fetchUser(ctx.params.id),
    fetchPosts(ctx.params.id),
  ]);
  return { props: { user, posts } };
}

// ❌ 串行（浪费 ~2x 时间）
const user  = await fetchUser(id);
const posts = await fetchPosts(id);
cached

2. 缓存策略

HTTP 缓存

设置 Cache-Control 头。静态页面用 s-maxage=31536000 + CDN；动态页面用 s-maxage=60, stale-while-revalidate。

Full Route Cache

Next.js App Router 自动缓存静态 RSC payload。动态路由用 unstable_cache() 包裹数据库查询。

数据缓存

React fetch 自动缓存同请求。自定义数据源用 Redis / Memcached 做应用层缓存。

stale-while-revalidate

先返回缓存，后台异步更新。用户永远不等，数据最终一致。

security

3. 安全实践

  • 防止 XSS：React 默认转义 HTML，但 dangerouslySetInnerHTML 必须配合 DOMPurify
  • CSP 配置：SSR 会产生 inline script（序列化数据），需用 nonce 或 hash 白名单
  • 环境变量隔离：只有 NEXT_PUBLIC_ 前缀的变量会暴露给客户端
  • SSRF 防护：服务端 fetch 用户可控 URL 时，必须校验目标域名白名单
// CSP nonce 示例（Express + React 18）
app.use((req, res, next) => {
  const nonce = crypto.randomUUID();
  res.setHeader('Content-Security-Policy',
    `script-src 'self' 'nonce-${nonce}'`
  );
  res.locals.nonce = nonce;
  next();
});
monitoring

4. 性能监控 & 度量

  • TTFB（Time to First Byte）：服务端处理时间，目标 < 200ms
  • FCP（First Contentful Paint）：用户首次看到内容，SSR 的核心优势
  • LCP（Largest Contentful Paint）：最大内容绘制，目标 < 2.5s
  • TTI（Time to Interactive）：Hydration 完成时间，SSR 可能比 CSR 更晚
  • INP（Interaction to Next Paint）：交互响应速度，关注 Hydration 阶段的长任务
warning
注意：SSR 改善 FCP/LCP 但可能恶化 TTI——因为 Hydration 需要下载并执行更多 JS。使用 Selective Hydration（React 18 Suspense）可以优先 hydrate 交互区域。
deploy

5. 部署架构

  • 容器化部署：Node.js SSR 服务打包为 Docker 镜像，K8s 编排，支持水平扩展
  • Serverless：Vercel / AWS Lambda，按请求计费，冷启动问题需注意（< 250ms）
  • Edge Functions：Cloudflare Workers / Vercel Edge，全球分布，延迟最低，但 API 受限（无 Node.js 原生模块）
  • CDN + SSR 混合：静态资源走 CDN，动态页面走 SSR，用 stale-while-revalidate 缓存 SSR 输出

6. 面试回答 Checklist

当被问到"你了解 SSR 么？有什么最佳实践？"时，按以下框架回答：

  1. 定义 + 动机：服务端渲染是什么，为什么需要（首屏性能 + SEO）
  2. 核心流程：请求 → 数据获取 → 渲染 HTML → 返回 → Hydration
  3. 关键技术：renderToString / renderToPipeableStream / Suspense 流式
  4. 最佳实践（挑 3-4 个展开）：
    • 数据并行获取、只传必要数据
    • 多级缓存（HTTP / Route / Data / SWR）
    • Hydration 陷阱规避
    • Selective Hydration 优化 TTI
  5. 模式对比：SSR vs SSG vs ISR vs RSC，什么场景用什么
  6. 实战经验：结合项目说踩过的坑（如 hydration mismatch、TTFB 优化）

渲染模式全景对比

🔴 SSR

每次请求都在服务端渲染。数据实时，但服务器压力大。适合：仪表盘、个性化页面。

🟢 SSG

构建时生成静态 HTML。速度最快，但数据是构建时快照。适合：博客、文档、营销页。

🟡 ISR

静态页面按需重新生成。兼顾 SSG 性能和数据新鲜度。适合：电商商品页、新闻列表。

🔵 RSC

React Server Components，组件级服务端渲染，零客户端 JS。与 SSR 互补，不是替代。
