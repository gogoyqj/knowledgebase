security

什么是服务安全？

服务安全是指通过一系列技术手段和管理措施，保护服务的机密性（Confidentiality）、 完整性（Integrity）和可用性（Availability），即经典的 CIA 三元组。 现代服务安全是一个多层次的纵深防御体系，从网络边界到代码逻辑，每一层都有对应的安全策略。

lightbulb
安全不是单一产品，而是一个持续的过程。需要从设计阶段就考虑安全（Security by Design），并在整个生命周期中不断评估和改进。
layers

纵深防御模型

纵深防御（Defense in Depth）是安全架构的核心理念：不依赖单一防线，而是在每一层都部署安全措施，即使某一层被突破，其他层仍能提供保护。

🌐 网络层安全
防火墙、DDoS 防护、VPN、网络隔离
🚪 传输层安全
TLS/SSL、证书管理、HTTPS 强制
🔑 身份层安全
认证、授权、会话管理、MFA
🛡️ 应用层安全
输入校验、参数化查询、安全头
💾 数据层安全
加密存储、脱敏、备份、访问控制
📋 运维层安全
日志审计、监控告警、漏洞管理、应急响应
checklist

CIA 三元组

visibility_off 机密性

确保数据只能被授权的人员访问。措施：加密、访问控制、数据脱敏、密钥管理。

verified 完整性

确保数据不被未授权篡改。措施：数字签名、哈希校验、版本控制、审计日志。

cloud_done 可用性

确保服务在需要时可正常访问。措施：负载均衡、容灾备份、DDoS 防护、限流熔断。

根据 OWASP Top 10，Web 应用最常见的安全风险包括：

🔓 失效的访问控制

越权访问、IDOR、权限提升。最常见且影响最大的安全问题。

📝 日志与监控不足

安全事件无法被及时发现和响应。

认证 vs 授权

认证（Authentication）和授权（Authorization）是安全体系中最基础的两个概念：

🔍 认证 Authentication

  • 你是谁？ — 验证身份
  • 发生在授权之前
  • 方式：密码、Token、生物识别
  • 结果：已认证 / 未认证

✅ 授权 Authorization

  • 你能做什么？ — 检查权限
  • 发生在认证之后
  • 方式：RBAC、ABAC、ACL
  • 结果：允许 / 拒绝

Session vs Token 认证

🍪 Session 认证

  • 服务端存储会话状态
  • 通过 Cookie 传输 Session ID
  • 天然支持会话管理和失效
  • 分布式环境需要共享存储（Redis）
  • 需要 CSRF 防护

🎫 Token 认证（JWT）

  • 无状态，服务端不存储会话
  • 通过 Header 传输：Authorization: Bearer xxx
  • 天然跨域、适合微服务
  • 失效需借助黑名单或短过期时间
  • 无 CSRF 问题（不依赖 Cookie）
tips_and_updates
最佳实践：Access Token（短期，15min）+ Refresh Token（长期，7d）双 Token 方案。Access Token 用于请求认证，Refresh Token 用于无感刷新。

RBAC 权限模型

基于角色的访问控制（Role-Based Access Control）是企业应用中最常用的授权模型：

┌─────────────────────────────────────────────────────────┐ │ RBAC 模型 │ └─────────────────────────────────────────────────────────┘ ┌──────────┐ ┌──────────┐ ┌──────────────┐ ┌──────────┐ │ User │───▶│ Role │───▶│ Permission │───▶│ Resource │ │ │ │ │ │ │ │ │ │ 张三 │ │ 管理员 │ │ user:read │ │ 用户管理 │ │ 李四 │ │ 编辑 │ │ user:write │ │ 文章管理 │ │ 王五 │ │ 访客 │ │ article:* │ │ 评论管理 │ └──────────┘ └──────────┘ └──────────────┘ └──────────┘ 用户 ──(N:N)──▶ 角色 ──(N:N)──▶ 权限 ──(N:N)──▶ 资源
// RBAC 中间件示例
function authorize(...requiredPermissions) {
  return (req, res, next) => {
    const user = req.user // 从认证中间件获取
    const userPermissions = getPermissionsByRoles(user.roles)

    const hasPermission = requiredPermissions.some(
      perm => userPermissions.includes(perm)
    )

    if (!hasPermission) {
      return res.status(403).json({
        error: 'Forbidden',
        message: '权限不足'
      })
    }
    next()
  }
}

// 使用
router.get('/users', authenticate, authorize('user:read'), getUsers)
router.delete('/users/:id', authenticate, authorize('user:delete'), deleteUser)

多因素认证（MFA）

MFA 要求用户提供两种或以上的验证因素，大幅提升账户安全性：

🧠 知识因素

用户知道的信息：密码、PIN 码、安全问题。

📱 持有因素

用户拥有的物品：手机（TOTP/SMS）、硬件密钥（YubiKey）、智能卡。

👆 固有因素

用户的生物特征：指纹、面部识别、虹膜、声纹。

TLS（Transport Layer Security）是保护网络通信安全的基石，HTTPS = HTTP + TLS。

TLS 1.3 改进：握手从 2-RTT 减少到 1-RTT（0-RTT 恢复），移除了不安全的密码套件（RC4、3DES、CBC），仅支持前向保密（PFS）。

import fs from 'node:fs'

  key: fs.readFileSync('./certs/server.key'),

  // 安全配置

  ciphers: [
    'TLS_AES_256_GCM_SHA384',
    'TLS_CHACHA20_POLY1305_SHA256',
    'ECDHE-RSA-AES256-GCM-SHA384'
  ].join(':'),
  honorCipherOrder: true
}, app)

对称加密 vs 非对称加密

🔑 对称加密

  • 加密解密使用同一密钥
  • 速度快，适合大量数据
  • 算法：AES-256-GCM、ChaCha20
  • 难点：密钥分发

🔐 非对称加密

  • 公钥加密，私钥解密
  • 速度慢，适合少量数据
  • 算法：RSA-2048、ECDSA (P-256)
  • 用途：密钥交换、数字签名
// Node.js 加密实践
import crypto from 'node:crypto'

// AES-256-GCM 对称加密
function encrypt(plaintext, key) {
  const iv = crypto.randomBytes(12)
  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv)
  let encrypted = cipher.update(plaintext, 'utf8', 'hex')
  encrypted += cipher.final('hex')
  const authTag = cipher.getAuthTag().toString('hex')
  return { iv: iv.toString('hex'), encrypted, authTag }
}

// 密码哈希（bcrypt / argon2）
import bcrypt from 'bcrypt'

const hash = await bcrypt.hash(password, 12) // salt rounds = 12
const match = await bcrypt.compare(inputPassword, storedHash)
warning
永远不要使用 MD5/SHA1 存储密码，它们不是密码哈希函数。使用 bcrypt、argon2 或 scrypt，它们内置 salt 和可调节的工作因子。

SQL 注入

SQL 注入是最古老也最危险的攻击方式之一，攻击者通过在输入中插入恶意 SQL 片段来操控数据库。

❌ 危险写法

  • 字符串拼接 SQL
  • 直接将用户输入嵌入查询
// 危险！
const sql = `SELECT * FROM users
  WHERE name = '${req.query.name}'`
// 输入: ' OR 1=1 --
// 结果: SELECT * FROM users WHERE name = '' OR 1=1 --'

✅ 安全写法

  • 参数化查询 / 预编译语句
  • 使用 ORM 的安全接口
// 安全！参数化查询
const result = await db.query(
  'SELECT * FROM users WHERE name = $1',
  [req.query.name]
)
code

XSS（跨站脚本攻击）

XSS 攻击者将恶意脚本注入到网页中，在其他用户的浏览器上执行。

📝 存储型 XSS

恶意脚本存储在数据库中，所有访问该页面的用户都会执行。危害最大。

🔗 反射型 XSS

恶意脚本在 URL 参数中，服务器将其反射回页面。需要诱导用户点击链接。

⚡ DOM 型 XSS

前端 JS 直接操作 DOM 时未转义用户输入，完全在客户端发生。

// XSS 防御措施

// 1. 输出编码（HTML Entity）
function escapeHtml(str) {
  return str
    .replace(/&/g, '&')
    .replace(/</g, '<')
    .replace(/>/g, '>')
    .replace(/"/g, '"')
    .replace(/'/g, ''')
}

// 2. CSP（Content Security Policy）响应头
res.setHeader('Content-Security-Policy',
  "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'"
)

// 3. 使用前端框架的自动转义（React/Vue 默认转义）
// React: {userInput} 自动转义
// Vue: {{ userInput }} 自动转义
// 危险: v-html / dangerouslySetInnerHTML

CSRF（跨站请求伪造）

攻击者诱导已登录用户在不知情的情况下发送恶意请求。

┌──────────────────────────────────────────────────────────────┐ │ CSRF 攻击流程 │ └──────────────────────────────────────────────────────────────┘ 1. 用户登录 bank.com，浏览器保存 Cookie 2. 用户访问 evil.com（攻击者控制的网站） 3. evil.com 页面中嵌入： <img src="https://bank.com/transfer?to=attacker&amount=10000"> 4. 浏览器自动携带 bank.com 的 Cookie 发送请求 5. bank.com 以为是合法请求，执行转账
// CSRF 防御方案

// 1. CSRF Token（最常用）
import csurf from 'csurf'
app.use(csurf({ cookie: true }))

// 2. SameSite Cookie 属性
res.cookie('session', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'Lax'  // Strict | Lax | None
})

// 3. 验证 Origin / Referer 头
app.use((req, res, next) => {
  const origin = req.headers.origin
  if (!ALLOWED_ORIGINS.includes(origin)) {
    return res.status(403).json({ error: 'Invalid origin' })

DDoS 攻击与防护

分布式拒绝服务攻击通过大量请求耗尽服务资源，使其无法响应正常用户。

🌊 流量型攻击

SYN Flood、UDP Flood、ICMP Flood。用海量流量淹没带宽。在网络层防护。

🔗 协议型攻击

Slowloris、HTTP Flood。利用协议漏洞消耗连接资源。在传输层防护。

💥 应用层攻击

CC 攻击、API 滥用。模拟正常请求消耗计算资源。在应用层防护。

// 应用层限流防护
import rateLimit from 'express-rate-limit'

// 全局限流：每 IP 每 15 分钟最多 100 次请求
const limiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 100,
  standardHeaders: true,
  legacyHeaders: false,
  message: { error: '请求过于频繁，请稍后再试' }
})
app.use('/api/', limiter)

// 登录接口更严格的限流
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5,
  skipSuccessfulRequests: true
})
app.use('/api/login', loginLimiter)

SSRF（服务端请求伪造）

攻击者利用服务端发起请求的功能，访问内部网络资源或云元数据。

warning
典型案例：2019 年 Capital One 数据泄露事件，攻击者利用 SSRF 访问 AWS 元数据服务 http://169.254.169.254 获取 IAM 临时凭证，最终泄露 1 亿用户数据。
// SSRF 防御
function isAllowedUrl(url) {
  const parsed = new URL(url)

  // 1. 只允许 HTTP/HTTPS 协议
  if (!/^https?:$/.test(parsed.protocol)) return false

  // 2. 禁止访问内网地址
  const hostname = parsed.hostname
  if (
    hostname === 'localhost' ||
    hostname.startsWith('127.') ||
    hostname.startsWith('10.') ||
    hostname.startsWith('172.16.') ||
    hostname === '169.254.169.254'  // AWS 元数据
  ) return false

  // 3. DNS 解析后再次检查（防止 DNS Rebinding）
  const addresses = dns.lookupAll(hostname)
  for (const addr of addresses) {
    if (isPrivateIP(addr.address)) return false
  }

  return true
}

安全 HTTP 响应头

正确配置 HTTP 安全头是防御多种攻击的低成本高收益措施：

// 使用 Helmet.js 设置安全响应头
import helmet from 'helmet'

app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'", "'unsafe-inline'"],
      imgSrc: ["'self'", 'data:', 'https:'],
      connectSrc: ["'self'", 'https://api.example.com']
    }
  },
  hsts: { maxAge: 31536000, includeSubDomains: true },
  referrerPolicy: { policy: 'strict-origin-when-cross-origin' }
}))

Strict-Transport-Security

强制浏览器使用 HTTPS，防止降级攻击。建议 max-age ≥ 1年。

Content-Security-Policy

限制页面可加载的资源来源，有效防御 XSS 和数据注入。

X-Content-Type-Options

设为 nosniff，防止浏览器 MIME 嗅探。

X-Frame-Options

设为 DENY 或 SAMEORIGIN，防止点击劫持。

输入验证与数据校验

永远不要信任客户端输入。所有外部数据都必须在服务端进行严格验证。

// 使用 Zod 进行输入验证
import { z } from 'zod'

const createUserSchema = z.object({
  name: z.string()
    .min(2, '名字至少 2 个字符')
    .max(50, '名字最多 50 个字符')
    .regex(/^[一-龥a-zA-Z]+$/, '只允许中英文'),

  email: z.string().email('邮箱格式不正确'),

  age: z.number()
    .int('必须是整数')
    .min(0, '年龄不能为负')
    .max(150, '年龄不合理'),

  role: z.enum(['user', 'admin', 'moderator'])
})

// 在路由中使用
app.post('/users', (req, res) => {
  const result = createUserSchema.safeParse(req.body)
  if (!result.success) {
    return res.status(400).json({
      errors: result.error.flatten().fieldErrors
    })
  }
  // result.data 已经过验证和类型转换
})
cookie

Cookie 安全配置

// Cookie 安全属性
res.cookie('session', token, {
  httpOnly: true,     // 禁止 JS 访问，防御 XSS 窃取
  secure: true,       // 仅通过 HTTPS 传输
  sameSite: 'Lax',    // 防御 CSRF（Strict 更安全但可能影响体验）
  maxAge: 2 * 60 * 60 * 1000,  // 2 小时过期
  path: '/',
  domain: '.example.com'
})

🔒 httpOnly

阻止 JavaScript 通过 document.cookie 读取，防止 XSS 窃取令牌。

🛡️ secure

Cookie 仅通过 HTTPS 连接传输，防止中间人窃听。

🚫 sameSite

控制跨站请求是否携带 Cookie，Lax 平衡安全与体验。

⏱️ 短过期时间

减少令牌泄露后的攻击窗口，配合 Refresh Token 无感续期。

日志审计与监控

完善的安全监控体系是发现和响应安全事件的关键。

📊 安全事件日志

记录登录失败、权限拒绝、异常请求等安全事件，包含时间、IP、用户、动作。

🚨 实时告警

暴力破解检测、异常流量告警、敏感操作通知（如密码修改、权限变更）。

📈 行为分析

建立用户行为基线，检测异常模式：非常规时间登录、异地访问、批量操作。

🔍 日志脱敏

日志中不记录密码、Token 等敏感信息。手机号、身份证号等进行脱敏处理。

// 安全日志中间件
function securityLogger(req, res, next) {
  const start = Date.now()

  res.on('finish', () => {
    const log = {
      timestamp: new Date().toISOString(),
      method: req.method,
      path: req.path,
      status: res.statusCode,
      ip: req.ip,
      userAgent: req.headers['user-agent'],
      userId: req.user?.id,
      duration: Date.now() - start
    }

    // 4xx/5xx 记录到安全日志
    if (res.statusCode >= 400) {
      logger.warn('security_event', log)
    }
  })
  next()
}

安全检查清单

上线前对照以下清单进行安全自查：

✅ 认证与会话

密码使用 bcrypt/argon2 哈希存储；JWT 使用强密钥并设置合理过期时间；实现 MFA。

✅ 传输安全

全站 HTTPS；TLS 1.2+；HSTS 开启；证书自动续期。

✅ 输入验证

所有外部输入服务端验证；参数化查询；输出编码；文件上传限制类型和大小。

✅ 依赖管理

定期 npm audit；锁定依赖版本；自动化漏洞扫描。

✅ 配置安全

敏感信息使用环境变量；生产环境关闭调试模式和详细错误信息。

✅ 监控响应

安全日志完整且脱敏；告警规则覆盖关键场景；有应急响应预案。

安全是一个持续演进的过程，没有绝对安全的系统，只有不断完善的防御
