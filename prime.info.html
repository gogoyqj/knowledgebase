核心思路：Python 是薄壳，TS 是引擎

Python skill 自身不直接持有 API key、不直接调 LLM API。所有需要 host 能力的操作，都通过 Jupyter Comm（ipykernel 的双向通信通道）转发回 TypeScript 侧执行。

Client 是瘦客户端，不执行 agent 逻辑

prime-agent 的 client（CLI / IDE 插件 / Web UI）只负责 UI 渲染和用户输入。所有 agent 逻辑都在 Daemon 进程中执行，Daemon 通过 spawn 为每个 session 创建独立的 Worker 子进程。

JSONL over Unix Socket

Client 与 Daemon 之间通过 Unix socket 通信，协议为 JSONL（每行一个 JSON 对象）。当前版本：DAEMON_PROTOCOL_VERSION = 7，schema revision 16。

launchWorker() — Supervisor 如何创建 Worker

源码位于 daemon-supervisor.ts:2157，关键步骤：

// 1. 构建启动参数
const launch = createCliSubprocessLaunchSpec(["--mode", "daemon", "--daemon-socket", socketPath]);

// 2. 设置 worker 环境变量
const workerEnvironment = createCliSubprocessEnv({
  ...process.env,
  DAEMON_WORKER_ROLE_ENV: "1",
  DAEMON_WORKER_TOKEN_ENV: token,
  DAEMON_WORKER_ACTIVE_SESSION_ID_ENV: rootActiveSessionId,
  DAEMON_WORKER_SUPERVISOR_SOCKET_ENV: this.socketPath,
  DAEMON_WORKER_RECOVERY_JOURNAL_ENV: recoveryJournalPath,
  ...
});

// 3. spawn 独立进程
const child = spawn(launch.command, launch.args, {
  cwd: config.cwd ?? process.cwd(),
  detached: true,       // 独立进程组
  env: workerEnvironment,
  stdio: ["ignore", "ignore", "pipe", "pipe"],
});

Worker 独立性

独立 socket

每个 worker 有自己的 Unix socket 路径，daemon 通过它与 worker 通信。

认证 token

每个 worker 分配随机 authenticationToken，防止未授权连接。

Recovery Journal

worker 崩溃后可从 journal 恢复 session 状态，不丢失上下文。

Client 断开不影响 Agent

Client 断开连接时，Daemon 和 Worker 继续运行。Client 重新 attach 即可接上正在进行的 session。这就是为什么需要 session recovery、orphan process journal 等机制。

balance 设计权衡 — Pros & Cons

Python Skill 桥接架构

thumb_up Pros

  • 安全隔离 — Python 不持有 API key，skill 代码无法直接访问 LLM 资源，降低泄露风险
  • 单一事实来源 — session 状态、模型配置、harness 数据全由 TS 侧管理，避免双端状态不一致
  • Python 生态复用 — 直接使用 pandas/numpy/scipy 等成熟库做数据处理，不需要 TS 重写
  • Skill 可插拔 — Python skill 通过 pyproject.tomx 声明依赖，syncPythonSkills() 按需安装，不污染基础环境
  • 统一 agent 模型 — rlm.run() 让 Python skill 也能 spawn 子 agent，TS/Python 侧能力一致

thumb_down Cons

  • Comm 延迟 — 每次 host_request 走 Jupyter Comm 往返，比进程内调用多一跳序列化/反序列化
  • 调试困难 — 跨进程桥接链路长（Python → Comm → TS handler），错误堆栈不连续，定位问题成本高
  • ipykernel 耦合 — 桥接强依赖 ipykernel 的 Comm 机制，kernel 版本变动可能 break 兼容性
  • 异步复杂度 — Python 侧所有 rlm 调用都是 async，skill 作者必须熟悉 asyncio，否则容易写出阻塞代码卡住 kernel
  • 冷启动成本 — 首次运行需 uv 安装 Python + 创建 venv + 装依赖，约 30s；venv 本身也占磁盘空间

Daemon 多进程架构

thumb_up Pros

  • Session 持久性 — client 断开不影响 agent 运行，re-attach 即恢复，支持长时间任务（小时级）
  • 进程隔离 — 每个 session 独立进程，一个 session crash 不影响其他 session 和 daemon 本身
  • Client 无关性 — CLI、IDE 插件、Web UI 都走同一协议，任意 client 可连接任意 session
  • Recovery 机制 — recovery journal + orphan process journal，worker 崩溃可重建状态，不丢失上下文
  • 多 session 并行 — daemon 同时管理多个 worker，各 session 独立运行互不阻塞

thumb_down Cons

  • 内存开销 — 每个 worker 是独立 Node.js 进程，N 个 session ≈ N 份 V8 heap，空闲 session 也占内存（需 eviction 策略）
  • 架构复杂度高 — supervisor → worker → kernel 三层进程，涉及 socket 通信、token 认证、journal 恢复、orphan 清理等大量机制
  • 协议维护成本 — JSONL 协议已到 schema revision 16，向后兼容约束让演进变慢，每改一版需考虑旧 client
  • 调试链路长 — 问题可能出在 client → daemon socket → worker → kernel comm 任一环节，日志分散在多个进程
  • 启动延迟 — 创建 session 需 spawn worker 子进程 + 可能的 kernel 初始化，首 token 延迟比 in-process 模式更高

设计哲学总结

维度 Python Skill 桥接 Daemon 多进程
核心目标 复用 Python 生态 + 安全隔离 Session 持久化 + 多端连接
隔离粒度 语言级 Python ↔ TS 运行时隔离 进程级 session 间进程隔离
状态管理 TS 侧单一事实源，Python 是无状态执行器 Daemon 集中管理，Worker 持有 session 状态
复杂度代价 Comm 桥接 + asyncio 要求 三层进程 + 协议版本管理
典型瓶颈 频繁 host_request 的序列化开销 多 session 内存压力
共同点 两者都用「瘦执行层 + 集中控制」模式 — 执行端不持有关键资源，核心逻辑收敛到 TS host
