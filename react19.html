React 19 概览

React 19 是 React 历史上最大的版本更新之一，引入了 React Compiler、 Server Components 正式稳定、全新的 Actions 机制， 以及多个新 Hooks。这些变化从根本上改变了 React 应用的编写方式。

lightbulb
React 19 的核心理念：让开发者专注于业务逻辑。通过编译器自动优化、服务端渲染原生支持、简化的状态管理，减少样板代码和心智负担。

Actions 与异步状态

React 19 引入了 Actions 概念——一种处理异步操作的全新方式，告别繁琐的 loading/error 状态管理：

// React 19: Actions 自动管理 pending 状态
function UpdateName() {
  const [name, setName] = useState("");
  const [error, submitAction, isPending] = useActionState(
    async (prev, formData) => {
      const error = await updateName(formData.get("name"));
      if (error) return error;
      redirect("/profile");
      return null;
    },
    null
  );

  return (
    <form action={submitAction}>
      <input name="name" />
      <button disabled={isPending}>
        {isPending ? "更新中..." : "更新"}
      </button>
      {error && <p>{error}</p>}
    </form>
  );
}
check_circle
告别 useEffect 地狱：Actions 将异步操作与 UI 事件直接绑定，React 自动管理 pending 状态和乐观更新。

实现原理：Actions 与 useActionState

Actions 并非全新的运行时概念，而是将异步状态机内置到 React 的更新调度中：

┌─────────────────────────────────────────────┐ │ useActionState 内部状态机 │ └─────────────────────────────────────────────┘ 用户触发 action (form submit / onClick) │ ▼ ┌─────────────┐ │ IDLE │ isPending = false │ (空闲态) │ └──────┬──────┘ │ dispatch(action) ▼ ┌─────────────┐ │ PENDING │ isPending = true │ (等待态) │ React 标记为 Transition └──────┬──────┘ │ ┌────┴────┐ │ │ resolve reject │ │ ▼ ▼ ┌───────┐ ┌───────┐ │ DONE │ │ ERROR │ 返回值 → state │ 成功 │ │ 失败 │ isPending = false └───────┘ └───────┘

关键实现细节：

  • 每个 useActionState 对应 Fiber 上的一个 queue（同 useReducer），但 dispatch 的是 async function
  • action 被包装在 startTransition 中执行，属于低优先级更新，不阻塞用户输入
  • 多次快速触发 action 时，React 自动取消前一个未完成的 Transition（类似竞态处理）
  • 返回的 isPending 来自 SharedState，同一 form 下的 useFormStatus 可以共享
// React 源码简化：useActionState 核心逻辑
function useActionState(action, initialState) {
  const queue = ensureUpdateQueue(fiber);  // 复用 update queue

  const dispatch = (payload) => {
    startTransition(() => {               // 低优先级
      const result = action(queue.lastRenderedState, payload);
      if (isThenable(result)) {            // 异步 action
        queue.pendingTransition = result;
        result.then(
          (v) => dispatchSetState(fiber, v),
          (e) => dispatchSetState(fiber, e)
        );
      } else {
        dispatchSetState(fiber, result);   // 同步 action
      }
    });
  };

  return [queue.lastRenderedState, dispatch, isPending];
}

实现原理：use() 与 Suspense 协作

use() 是 React 中第一个可以在条件语句中调用的"类 Hook"，它的实现绕过了 Hooks 规则的限制。

lightbulb
核心机制：throw promise + Suspense catch。这和 React.lazy()、Suspense for Data Fetching 是完全相同的底层模式——当 Promise 还没 resolve 时，use() 直接 throw 这个 Promise，最近的 Suspense 边界会 catch 住它并显示 fallback。Promise resolve 后，React 重新渲染该 Suspense 子树，use() 返回缓存值。唯一的区别是 Promise 状态缓存在 Promise 对象本身（promise._reactInternals.status），而非 Fiber 的 hook 链表，所以不受调用顺序约束。
┌─────────────────────────────────────────────┐ │ use() 执行流程 │ └─────────────────────────────────────────────┘ 组件渲染 │ ▼ use(promise) │ ├── promise.status === "fulfilled" │ │ │ ▼ │ 返回 promise.value ← 有缓存，直接返回 │ ├── promise.status === "rejected" │ │ │ ▼ │ throw promise.reason ← 传播到 Error Boundary │ └── promise.status === "pending" │ ▼ throw promise ← Suspense 捕获 │ ▼ ┌──────────┐ │ Suspense │ 显示 fallback │ boundary │ └────┬─────┘ │ promise resolve │ ▼ 重新渲染 Suspense 子树 use() 返回结果
// React 源码简化：use() 核心实现
function use(usable) {
  if (usable !== null && typeof usable === 'object') {
    // 处理 Promise — 直接在 Promise 对象上挂载 React 内部状态
    switch (usable._status) {
      case 1:                           // fulfilled
        return usable._value;
      case 2:                           // rejected
        throw usable._value;
      default:
        throw usable;                   // Suspense 捕获
    }
  }
}
warning
Promise 污染问题：React 会在传入的 Promise 上直接写入 _status、_value 等私有属性，相当于 mutate 了外部对象。这意味着：
• 同一个 Promise 被多个组件 use() 时会共享缓存（这通常是期望行为）
• Promise 即使 resolve 后仍持有 React 内部引用，不会被自动清理
• 如果 Promise 被持久化（如缓存到 Map 中），其上的 React 内部属性会泄漏到应用生命周期之外
• 第三方库如果也往 Promise 上挂属性，可能产生命名冲突
lightbulb
为什么 use() 可以在条件语句中调用？因为它不使用 Fiber 的 hook 链表（linked list），而是将状态绑定到 Promise 对象本身。传统 Hooks 依赖调用顺序来匹配 state slot，use() 通过 Promise 引用直接定位状态。

实现原理：useOptimistic 乐观更新

useOptimistic 在底层维护两层状态——基础状态和乐观覆盖层：

┌─────────────────────────────────────────────┐ │ useOptimistic 双层状态模型 │ └─────────────────────────────────────────────┘ ┌─────────────────────────────┐ │ baseState (来自 props) │ ← 权威状态 │ [A, B, C] │ └──────────────┬──────────────┘ │ │ + optimistic action ▼ ┌─────────────────────────────┐ │ optimisticState (合并后) │ ← UI 显示 │ [A, B, C, D⏳] │ (乐观值) └──────────────┬──────────────┘ │ 异步完成 │ ▼ ┌─────────────────────────────┐ │ baseState 更新 (真实数据) │ ← 乐观层清空 │ [A, B, C, D] │ 回归权威状态 └─────────────────────────────┘
// React 源码简化：useOptimistic 核心逻辑
function useOptimistic(passthrough, reducer) {
  const [state, dispatch] = useReducer(
    (currentState, action) => {
      if (action === '__RESET__') {
        return passthrough;       // 异步完成，重置为真实值
      }
      return reducer(currentState, action);
    },
    passthrough
  );

  // 当 passthrough 变化时自动重置（异步操作完成）
  useEffect(() => {
    dispatch('__RESET__');
  }, [passthrough]);

  const addOptimistic = (action) => dispatch(action);

  return [state, addOptimistic];
}
lightbulb
竞态安全：useOptimistic 的乐观状态是通过 reducer 函数派生的，多个乐观操作可以叠加。当真实 props 更新时（Server Action 完成），useEffect 自动重置乐观层，保证最终一致性。

实现原理：useFormStatus 与 Ref 清理

useFormStatus 并不通过 props 传递状态，而是利用 React 的内部 Context 机制：

  • 当 <form> 拥有 action 属性时，React 自动创建一个 FormStatusContext
  • form 提交时，React 将 { pending, data, method, action } 写入该 Context
  • useFormStatus() 内部调用 readContext(FormStatusContext)，绕过 props drilling
  • 状态更新被标记为 SyncLane（同步优先级），确保 pending 指示器立即响应
lightbulb
为什么 useFormStatus 只能用在 form 内部？因为它读取的是最近祖先 <form> 创建的 Context。在 form 外部调用会读到默认值 { pending: false }，不会报错但无意义。

Ref 清理函数的实现变更在 Commit 阶段：

// React 18: ref 回调无清理机制
<div ref={(el) => { observer.observe(el); }} />
// 组件卸载时需要 useEffect 手动清理 ↑

// React 19: ref 回调可返回清理函数
<div ref={(el) => {
  observer.observe(el);
  return () => observer.unobserve(el);  // 自动在卸载时调用
}} />

// 源码简化：Commit 阶段 ref 处理变更
function commitRefCleanup(ref, instance) {
  if (typeof ref === 'function') {
    // React 19: 先调用旧 cleanup，再调用新 ref
    const cleanup = ref.currentCleanup;
    if (cleanup) cleanup();           // ← 新增：清理旧 ref
    const newCleanup = ref(instance);  // 调用新 ref
    ref.currentCleanup =               // 缓存清理函数
      typeof newCleanup === 'function' ? newCleanup : null;
  }
}

useSyncExternalStore：谁才是"外部"？

useSyncExternalStore 解决一个特定问题：把 React 管不了的状态安全地同步进渲染流程。

info
React 官方立场："When possible, we recommend using built-in React state with useState and useReducer instead. The useSyncExternalStore API is mostly useful if you need to integrate with existing non-React code."
能用 useState/useReducer 就用，useSyncExternalStore 是给已有的非 React 代码兜底的。

那什么是"已有的非 React 代码"维护的状态？

✅ React 内部状态

  • useState / useReducer
  • Context + Provider
  • Redux（react-redux 内部已用 useSyncExternalStore）
  • Zustand / Jotai / Recoil（基于 React 原语）
  • Server Components 传递的 props

React 能感知变化，自动触发重渲染，无撕裂风险

⚠️ React 外部状态

  • 浏览器 API：localStorage、navigator.onLine、matchMedia
  • 全局变量 / 单例对象
  • WebSocket / SSE 推送的数据
  • 第三方非 React 库的状态（MobX observable、RxJS subject）
  • 跨 iframe / Web Worker 共享的数据

React 无感知，需要手动通知，有撕裂风险

lightbulb
判断标准：这个状态的源头是已有的非 React 代码吗？是 → useSyncExternalStore。不是 → useState/useReducer。本质上它是一个迁移/兼容工具，不是新项目的首选方案。

实际场景对比：

// ── 场景 1：纯 React 状态 → useState 就够了 ──
const [count, setCount] = useState(0);
// React 内部管理，自动调度重渲染

// ── 场景 2：浏览器 API → 必须用 useSyncExternalStore ──
import { useSyncExternalStore } from 'react';

function useMediaQuery(query) {
  return useSyncExternalStore(
    // subscribe: React 无法感知 matchMedia 变化，需要手动订阅
    (callback) => {
      const mql = matchMedia(query);
      mql.addEventListener('change', callback);
      return () => mql.removeEventListener('change', callback);
    },
    // getSnapshot: 返回可比较的快照（不能每次返回新对象）
    () => matchMedia(query).matches
  );
}

// ── 场景 3：Redux → 已经在用 useSyncExternalStore 了 ──
// react-redux 的 useSelector 源码：
function useSelector(selector) {
  return useSyncExternalStore(
    store.subscribe,              // Redux store 的订阅机制
    () => selector(store.getState())  // 从 store 读取并选择
  );
}

它解决的核心问题——并发渲染下的 tearing（撕裂）：

┌─────────────────────────────────────────────┐ │ 并发渲染中的 Tearing 问题 │ └─────────────────────────────────────────────┘ ── 没有 useSyncExternalStore ── 外部 store: { theme: "dark" } 组件树渲染（并发模式，可中断）： ┌─────────┐ │ Header │ 读取 store → "dark" ✓ 正确 └─────────┘ │ │ ← 此时外部 store 改为 "light" │ ┌─────────┐ │ Footer │ 读取 store → "light" ← 撕裂！ └─────────┘ Header 显示 dark 主题，Footer 显示 light 主题 同一次渲染中看到了不一致的状态 = Tearing ── 使用 useSyncExternalStore ── React 在渲染前对所有组件调用 getSnapshot() 如果任何 snapshot 变化，整个渲染重新开始 保证同一次渲染中所有组件读到同一版本的状态
// useSyncExternalStore 源码简化
function useSyncExternalStore(subscribe, getSnapshot) {
  const value = getSnapshot();           // 渲染时同步读取

  // 每次渲染都检查 snapshot 是否变化
  if (value !== lastSnapshot) {
    // snapshot 变了但不是因为本组件触发的
    // → 可能是其他组件更新期间 store 被改了
    // → 抛出异常，中断渲染，重新开始
    throw new Error('Store changed during render');
  }

  // commit 后订阅变化，触发同步更新（SyncLane）
  useEffect(() => {
    const unsubscribe = subscribe(() => {
      // store 变化 → 强制同步重渲染，不用 startTransition
      forceSyncRerender();
    });
    return unsubscribe;
  }, [subscribe]);

  return value;
}
warning
getSnapshot 的约束：必须返回可比较的值（原始类型或引用稳定的对象）。如果每次返回新对象 {...}，React 会认为状态永远在变，导致无限重渲染。
check_circle
结论：纯 React 项目中，优先用 useState/useReducer 管状态。只有当你需要接入已有的非 React 状态源（浏览器 API、遗留代码、第三方非 React 库）时，才用 useSyncExternalStore。Redux/Zustand 等现代 React 状态库已经在内部帮你处理了这些细节，你不需要直接调用它。

React Compiler 是什么？

React Compiler（原名 React Forget）是一个自动优化编译器， 它在构建时分析组件代码，自动插入 useMemo、 useCallback、memo 等优化， 开发者不再需要手动记忆化。

lightbulb
核心价值：将"何时优化"的决策从开发者转移到编译器。开发者写直观代码，编译器保证性能。
compare_arrows

编译前 vs 编译后

❌ 手动优化（React 18）

const Component = memo(() => {
  const data = useMemo(
    () => expensiveCalc(input),
    [input]
  );
  const handleClick = useCallback(
    () => doSomething(data),
    [data]
  );
  return <button onClick={handleClick}>...</button>;
});

✅ 编译器自动优化（React 19）

function Component() {
  const data = expensiveCalc(input);
  const handleClick = () => doSomething(data);
  return <button onClick={handleClick}>...</button>;
}

// 编译器自动插入 useMemo, useCallback, memo

┌─────────────────────────────────────────────┐ │ React Compiler 编译流程 │ └─────────────────────────────────────────────┘ 源代码 (.jsx/.tsx) │ ▼ ┌─────────────────┐ │ 1.   • 回调函数 → 自动 useCallback
  • 组件 → 自动 memo 包裹

Server Components 概述

React Server Components (RSC) 允许组件在服务器上渲染， 将 HTML 直接发送到客户端。Server Components 不发送 JavaScript 到浏览器， 显著减少 bundle 体积并提升首屏性能。

lightbulb
关键区别：Server Components ≠ SSR。SSR 是在服务端渲染 HTML 后 hydrate，RSC 是组件永远不发送 JS 到客户端。
compare_arrows

Server vs Client Components

🖥️ Client Component

  • 运行在浏览器
  • 可以使用 useState、useEffect
  • 可以绑定事件处理器
  • 可以访问浏览器 API
  • JS 会发送到客户端

☁️ Server Component

  • 仅运行在服务器
  • 不能使用 useState、useEffect
  • 可以直接访问数据库/文件系统
  • 零客户端 JS 开销
  • 可以 async/await
// Server Component (默认)
// app/page.tsx — 无需 "use client" 指令
async function UserProfile({ userId }) {
  // 直接访问数据库，不会发送到客户端
  const user = await db.user.findUnique({ where: { id: userId } });
  const posts = await db.post.findMany({ where: { authorId: userId } });

  return (
    <div>
      <h1>{user.name}</h1>
      <PostList posts={posts} />
      {/* 嵌套 Client Component */}
      <FollowButton userId={userId} />
    </div>
  );
}

// Client Component
"use client";
function FollowButton({ userId }) {
  const [following, setFollowing] = useState(false);
  return (
    <button onClick={() => setFollowing(!following)}>
      {following ? "已关注" : "关注"}
    </button>
  );
}

Server Actions

Server Actions 是在服务器上执行的函数，可以直接从 Client Components 调用：

// actions.ts — Server Action
"use server";

export async function createPost(formData) {
  const title = formData.get("title");
  const content = formData.get("content");

  // 直接操作数据库
  await db.post.create({
    data: { title, content, authorId: getUserId() }
  });

  revalidatePath("/posts");
  redirect("/posts");
}

// 客户端组件中使用
"use client";
import { createPost } from "./actions";

function NewPostForm() {
  return (
    <form action={createPost}>
      <input name="title" />
      <textarea name="content" />
      <button type="submit">发布</button>
    </form>
  );
}

Fiber 架构

React 的核心是 Fiber 架构——一种可中断的、增量式的渲染架构。 每个 React 元素对应一个 Fiber 节点，形成一棵 Fiber 树。

┌─────────────────────────────────────────────┐ │ Fiber 节点结构 │ └─────────────────────────────────────────────┘ FiberNode { tag: FunctionComponent | ClassComponent | ... type: Component | "div" | "span" | ... key: string | null stateNode: DOM | Fiber | ... ── 树结构 ── child: Fiber | null ← 第一个子节点 sibling: Fiber | null ← 下一个兄弟节点 return: Fiber | null ← 父节点 ── 工作状态 ── pendingProps: object ← 新 props memoizedProps: object ← 上次渲染的 props memoizedState: any ← 上次渲染的 state updateQueue: UpdateQueue ← 更新队列 ── 副作用 ── flags: number ← 副作用标记 subtreeFlags: number ← 子树副作用 lanes: Lanes ← 优先级标记 childLanes: Lanes ← 子树优先级 }

flags 位掩码 与 Hooks 副作用

为什么 flags 是一个数字而不是数组？因为它是位掩码（bitmask）——每个标记占一个 bit，用位运算组合：

// React 内部 flag 定义（简化）
const NoFlags          = 0b00000000000000;  // 0
const Placement        = 0b00000000000010;  // 2  — 新增节点
const Update           = 0b00000000000100;  // 4  — props 变化
const Deletion         = 0b00000000001000;  // 8  — 删除节点
const ChildDeletion    = 0b00000000100000;  // 32 — 子树有删除
const Ref              = 0b00000001000000;  // 64 — ref 变化
const Snapshot         = 0b00000100000000;  // 256
const Passive          = 0b00001000000000;  // 512 — 有 useEffect
const LayoutMask       = 0b00100100100100;  // useLayoutEffect 相关

// 位运算 — 极快，O(1)
fiber.flags |= Placement;              // 设置标记（OR）
if (fiber.flags & Placement) { ... }  // 检查标记（AND）
fiber.flags &= ~Update;                // 清除标记（AND NOT）

// 一次位运算可以同时检查多个 flag
if (fiber.flags & (Placement | Update | Deletion)) {
  // 这个 Fiber 有 DOM 操作需要执行
}
lightbulb
为什么不用数组？位运算只需一条 CPU 指令，数组的 includes/push 需要内存分配和遍历。一棵 Fiber 树可能有上万个节点，每个节点都要检查 flags，位掩码的性能优势在大规模应用中是数量级的。

但 hooks 的副作用（useEffect/useLayoutEffect）不直接存在 flags 里，它们走的是独立的环形链表：

┌─────────────────────────────────────────────┐ │ Fiber 节点上的两套副作用系统 │ └─────────────────────────────────────────────┘ FiberNode { flags: 0b00001000000110 ← 结构性副作用（位掩码） │ Placement + Update + Passive │ updateQueue: { ← Hooks 副作用（环形链表） │ lastEffect: ─────┐ │ │ │ ┌────────────────┘ │ ▼ │ Effect { │ tag: Passive | Layout | HookHasEffect │ create: () => { ... } ← useEffect 回调 │ destroy: () => { ... } ← cleanup 函数 │ deps: [a, b, c] ← 依赖数组 │ next: ──────▶ 下一个 Effect │ } │ │ Effect { │ tag: Layout | HookHasEffect │ create: () => { ... } ← useLayoutEffect 回调 │ destroy: null │ deps: [x] │ next: ──────▶ 回到第一个 Effect │ } └── } ── 两套系统如何协作 ── flags 中的 Passive bit: 0 → 该 Fiber 没有 useEffect，跳过 effect 遍历 1 → 该 Fiber 有 useEffect，需要遍历 updateQueue.lastEffect flags 中的 LayoutMask: 匹配 → 该 Fiber 有 useLayoutEffect，commit 阶段同步执行
// Commit 阶段简化流程 — 两套系统各自工作
function commitRoot(root) {
  // ── 第一步：处理结构性副作用（靠 flags 位掩码）──
  commitMutationEffects(root);   // DOM 增删改

  // ── 第二步：同步执行 Layout Effects ──
  commitLayoutEffects(root);
  // 遍历 Fiber 树，对每个节点：
  //   if (fiber.flags & LayoutMask) {
  //     遍历 fiber.updateQueue.lastEffect 环形链表
  //     执行 tag 包含 Layout 的 effect.destroy()
  //     执行 tag 包含 Layout 的 effect.create()
  //   }

  // ── 第三步：异步调度 Passive Effects ──
  if (root.finishedWork.flags & Passive) {
    scheduleCallback(() => {     // 浏览器空闲时执行
      flushPassiveEffects(root);
      // 遍历所有带 Passive flag 的 Fiber
      // 执行 useEffect 的 destroy → create
    });
  }
}
warning
Passive flag 是聚合标记：fiber.flags 上的 Passive bit 只是告诉 commit 阶段"这个 Fiber 有 useEffect 需要处理"，具体有几个 effect、依赖是什么、回调是什么，全部存在 updateQueue.lastEffect 的环形链表里。flags 是"要不要查"，链表是"查什么"。

Hooks 链表 vs Effects 链表：两条独立的链

不是所有 Hook 都是 Effect，也不是所有 Effect 都在 Hooks 链表上。一个 Fiber 节点上实际有两条链表：

┌─────────────────────────────────────────────────┐ │ 一个 Fiber 节点上的两条独立链表 │ └─────────────────────────────────────────────────┘ FiberNode { memoizedState ──────┐ ← Hook 链表头（所有 hooks） updateQueue ─────┐ │ │ │ │ ▼ │ ┌──────────────────────────────┐ │ │ Hook 链表 (singly linked list) │ │ │ 所有 hook 调用按顺序排列 │ │ └──────────────────────────────┘ │ ▼ ┌──────────────────────────────────┐ │ Effect 环形链表 (circular linked) │ │ 仅 useEffect / useLayoutEffect │ └──────────────────────────────────┘ } ── Hook 链表（memoizedState）── memoizedState │ ▼ Hook { memoizedState: 0, ← useState 的 state 值 queue: { pending: null }, next ──┐ } │ ◀─────────────────────────────────┘ │ ▼ Hook { memoizedState: [a,b], ← useMemo 的缓存值和依赖 queue: null, next ──┐ } │ ◀──────────────────────────────────┘ │ ▼ Hook { memoizedState: fn, ← useCallback 缓存的函数 queue: null, next ──┐ } │ ◀──────────────────────────────────┘ │ ▼ Hook { memoizedState: {current}, ← useRef 的 ref 对象 queue: null, next ──┐ } │ ◀─────────────────────────────────────┘ │ ▼ Hook { memoizedState: Effect, ← useEffect 在 hook 链表上的占位 queue: null, next: null } 但 effect 的实际内容不在这里 ──────────────┐ │ ── Effect 环形链表（updateQueue.lastEffect）── │ │ updateQueue.lastEffect │ │ ◀────────────────────────────────────────┘ ▼ ┌────────────────────────────┐ │ Effect { │ │ tag: Passive | HasEffect │ ← Passive = useEffect │ create: () => {...} │ ← 回调函数 │ destroy: cleanup │ ← 清理函数 │ deps: [a, b] │ ← 依赖数组 │ next: ──────────────────┼──▶ Effect { ... } │ } │ next ───▶ Effect { ... } └────────────────────────────┘ ◀──────┘ (环形)
// 每次组件渲染，React 按 hook 调用顺序遍历 hook 链表
// workInProgressHook 指针逐个推进
let workInProgressHook = null;

// useState — 在 hook 链表上创建带 queue 的 Hook 节点
function useState(initialState) {
  const hook = createWorkInProgressHook();  // 链表上取/建节点
  if (!hook.memoizedState) {
    hook.memoizedState = initialState;         // 首次渲染
  }
  hook.queue = { pending: null };             // 更新队列
  return [hook.memoizedState, dispatch];       // 推进指针
}

// useEffect — hook 链表上放一个占位节点，同时往 effect 环形链表上挂真正的 Effect
function useEffect(create, deps) {
  const hook = createWorkInProgressHook();  // hook 链表推进
  const effect = { tag: Passive, create, destroy: null, deps };
  hook.memoizedState = effect;                 // 占位（存引用）
  pushEffect(fiber.updateQueue, effect);      // 同时挂到 effect 环形链表
}

// useMemo — 只在 hook 链表上操作，不碰 effect 环形链表
function useMemo(nextCreate, deps) {
  const hook = createWorkInProgressHook();
  if (!depsChanged(hook.memoizedState.deps, deps)) {
    return hook.memoizedState.value;           // 依赖没变，返回缓存
  }
  const value = nextCreate();
  hook.memoizedState = { value, deps };
  return value;
}
lightbulb
总结：
• 所有 Hook（useState/useReducer/useMemo/useCallback/useRef/useEffect/useLayoutEffect）都在 memoizedState 的单向链表上，按调用顺序排列。这就是为什么 Hooks 不能放在条件语句里——断了顺序就找不到对应的节点。
• 只有 useEffect 和 useLayoutEffect 会额外往 updateQueue.lastEffect 的环形链表上挂 Effect 节点。
• Hook 链表上的 effect 节点只是一个引用/占位，真正的 create/deps/destruction 在环形链表上。
• Commit 阶段只遍历环形链表，不遍历 hook 链表。

双缓冲机制（Double Buffering）

React 维护两棵 Fiber 树：current（屏幕上的）和 workInProgress（正在构建的）。

┌─────────────────────────────────────────────┐ │ 双缓冲 Fiber 树 │ └─────────────────────────────────────────────┘ current 树 (屏幕显示) workInProgress 树 (构建中) │ │ ▼ ▼ App App │ │ ▼ ▼ ┌───┐ ┌───┐ │ A │ │ A'│ ← 克隆节点 └─┬─┘ └─┬─┘ │ │ ┌─┴──┐ ┌──┴─┐ │ B │ │ B' │ │ C │ │ C' │ └────┘ └────┘ 渲染完成后： current = workInProgress ← 指针交换（O(1)） workInProgress = current ← 旧树复用
lightbulb
为什么需要双缓冲？渲染过程可以中断，用户看到的永远是完整的 current 树。只有当 workInProgress 树完全构建完成后，才一次性切换，避免 UI 撕裂。

并发渲染（Concurrent Rendering）

React 18+ 引入并发渲染，允许多个版本的 UI 同时存在：

1. 优先级调度

用户输入（高优先级）可以中断低优先级的渲染（如数据加载）

2. 时间切片（Time Slicing）

将渲染工作分割成小块，每块 5ms，让出主线程给浏览器

3. 可中断渲染

Fiber 节点标记为"已完成"和"待处理"，中断后从断点恢复

4. 自动批处理（Automatic Batching）

多次 setState 合并为一次渲染，减少不必要的重绘

// 并发特性示例
function SearchResults({ query }) {
  const [deferredQuery, setDeferredQuery] = useState(query);

  // useTransition: 标记为低优先级更新
  const [isPending, startTransition] = useTransition();

  useEffect(() => {
    startTransition(() => {
      setDeferredQuery(query);  // 低优先级
    });
  }, [query]);

  // useDeferredValue: 延迟更新的值
  const deferredValue = useDeferredValue(query, { initialValue: "" });

  return (
    <div>
      {isPending && <Spinner />}
      <Results query={deferredValue} />
    </div>
  );
}

Reconciliation（协调算法）

React 通过比较新旧 Fiber 树来确定最小更新：

┌─────────────────────────────────────────────┐ │ Reconciliation 流程 │ └─────────────────────────────────────────────┘ 触发更新 (setState / props 变化) │ ▼ ┌─────────────────┐ │ 1. 创建/复用 │ workInProgress Fiber │ Fiber 节点 │ └────────┬────────┘ │ ▼ ┌─────────────────┐ │ 2. Diff 算法 │ 比较 key 和 type │ (O(n) 复杂度) │ 匹配旧 Fiber └────────┬────────┘ │ ▼ ┌─────────────────┐ │ 3. 标记副作用 │ Placement / Update / │ (Flags) │ Deletion / ChildDeletion └────────┬────────┘ │ ▼ ┌─────────────────┐ │ 4. 提交阶段 │ 一次性应用 DOM 变更 │ (Commit) │ 调用生命周期/Effects └────────┬────────┘ │ ▼ 交换 current 指针
lightbulb
Diff 策略：同级比较、类型不同直接替换、key 标识移动。单节点 Diff 时间复杂度 O(n)，这是 React 高性能的基础。

渲染三阶段

📋 Render 阶段

纯计算，可中断。遍历 Fiber 树，调用 render 函数，构建 workInProgress 树。不产生副作用。

🔍 Pre-commit 阶段

读取 DOM 快照（getSnapshotBeforeUpdate）。在 DOM 变更前捕获信息。

✅ Commit 阶段

不可中断。一次性应用 DOM 变更，调用 useEffect/useLayoutEffect，切换 Fiber 树。

React Activity（原 Offscreen）

允许组件在"隐藏"状态下保持状态，实现真正的后台渲染：

// 实验性 API
import { unstable_Activity as Activity } from 'react';

function App() {
  const [tab, setTab] = useState("home");

  return (
    <div>
      <TabBar active={tab} onChange={setTab} />

      {/* 隐藏的 tab 保持状态，不卸载 */}
      <Activity mode={tab === "home" ? "visible" : "hidden"}>
        <HomePage />
      </Activity>

      <Activity mode={tab === "profile" ? "visible" : "hidden"}>
        <ProfilePage />
      </Activity>
    </div>
  );
}
check_circle
优势：切换 tab 时不需要重新挂载和初始化，滚动位置、表单输入、动画状态全部保留。
