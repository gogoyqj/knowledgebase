dmux

Parallel agents with tmux and worktrees

多 Agent 并行开发利器

基于 tmux + git worktree，让多个 AI Agent 在同一仓库中隔离并行工作，互不冲突。

tmux 3.0+ Node.js 18+ Git 2.20+ MIT License

architecture 核心原理

每个 Agent 获得独立的 git worktree 和分支，从根源上消除冲突。

你的仓库 (main)
│
├── worktree-1 ── Claude Code
│   └── 分支: feature/auth
│
├── worktree-2 ── Codex
│   └── 分支: feature/api
│
└── worktree-3 ── Gemini CLI
    └── 分支: fix/bug-123

merge_type 合并冲突处理

dmux 采用两阶段合并策略，配合 AI 辅助或手动方式解决冲突。

两阶段合并策略

dmux 不是直接往 main 合并，而是分两步走，确保 main 分支永远不会出现冲突标记。

Phase 1: main ──→ worktree
  把 main 最新代码拉到 worktree
  在隔离环境中检测 / 解决冲突

Phase 2: worktree ──→ main
  冲突解决后，快进合并回 main
  （此时不可能再有冲突）
阶段方向目的
Phase 1main → worktree把 main 最新改动拉到 worktree，在隔离环境里检测/解决冲突
Phase 2worktree → main冲突解决后，快进合并回 main

触发合并

在 pane 上按 m，dmux 首先用 git merge-tree 模拟合并，在实际合并之前检测冲突。

你按 'm' 合并一个 worktree
        │
        ▼
 ┌──────────────────────┐
 │  预验证 (git merge-tree)  │
 │  模拟合并，检测冲突     │
 └──────────┬───────────┘
            │
    ┌───────┴───────┐
    │ 发现冲突？      │
    ├──── No ────────┤──── Yes ────┐
    │                │            │
    ▼                ▼            ▼
 直接合并       弹出选择对话框
 Phase 2        ┌──────────────┐
                │ ① AI 辅助合并  │
                │ ② 手动解决    │
                │ ③ 取消        │
                └──────────────┘

psychology 路径 A：AI 辅助合并

默认选项。dmux 自动创建冲突解决 pane，由 Agent 分析并解决冲突。

1
创建冲突解决 Pane

不开新 worktree，直接在原 worktree 目录创建新 tmux pane。冲突 pane 和原 pane 共享同一个文件系统。

2
启动 Agent 解决冲突

Claude Code 或 OpenCode 分析冲突文件，编辑解决，提交合并。

3
后台 Monitor 轮询

每 2 秒检查冲突是否已解决：未解决文件列表为空 + MERGE_HEAD 文件不存在。

4
自动清理

关闭冲突 pane → 重新执行 Phase 2 → 弹出清理对话框 → 关闭原 pane、删除 worktree、删除分支。

info
冲突 pane 和原 worktree pane 共享同一个文件系统，Agent 的修改实时可见，无需手动同步。
// conflictMonitor.ts — 每 2 秒轮询
areConflictsResolved():
  ✓ git diff --name-only --diff-filter=U 为空  // 没有未解决的冲突文件
  ✓ MERGE_HEAD 文件不存在                       // 合并已完成或中止

edit 路径 B：手动解决

你也可以选择自己手动处理冲突。

1
跳转到原 worktree Pane

dmux 自动导航到冲突所在的 pane。

2
手动编辑冲突文件

你自行编辑文件，解决 <<<<<<< 冲突标记。

3
提交并重试

git add + git commit，再按 m 重试合并。

4
验证通过，完成合并

这次冲突已解决，执行 Phase 2 合并回 main。

scenario 实际场景

两个 Agent 改了同一个文件，如何处理？

main (最新)
│
├── worktree-A (feature/auth)
│   └── 改了 utils.ts 第 10-20 行
│
└── worktree-B (feature/api)
    └── 改了 utils.ts 第 15-25 行

1. 先合并 A ──→ 无冲突 ✓
2. 再合并 B ──→ 检测到冲突！
   → 弹出对话框
   → 选 AI 辅助
   → Agent 在 worktree-B 解决冲突
   → 自动合并回 main ✓

webhook Lifecycle Hooks

在关键节点运行自定义脚本，增加额外保障。

Hook触发时机典型用途
worktree_created新 worktree 创建后安装依赖、初始化环境
pre_merge合并前（Phase 1 内）跑 typecheck、单元测试
post_merge合并完成后跑全量 CI、通知团队
pane_created新 pane 创建后自定义 pane 配置

pre_merge 能防什么？不能防什么？

pre_merge 检查范围:
┌──────────────────────────────┐
│  Agent 的改动 + 当前 main     │
│  = worktree 合并后的代码      │
│  → 在这里跑 typecheck + test  │
└──────────────────────────────┘
         ✓ 能拦截

累积效果:
┌──────────────────────────────┐
│  Agent A 已合并到 main        │
│  Agent B 再合并到 main        │
│  A + B 的组合可能有 bug       │
│  → pre_merge 检查不到         │
└──────────────────────────────┘
         ✗ 拦不住
手段能防防不了
pre_merge hook 单个 worktree 与 main 的集成问题 多个 worktree 合并后的累积问题
post_merge 跑全量 CI 所有已合并代码的组合问题 时序依赖、异步 bug
合并顺序控制 先合基础模块，再合依赖模块 语义层面的冲突
warning
pre_merge 是安全网，不是保证。要真正保证代码正确，应在每次合并后跑完整测试——在 post_merge hook 里做，或在 main 分支上跑 CI。

tips_and_updates 最佳实践

  1. 一个 pane 一个任务 — 保持 worktree 职责单一，降低冲突概率。
  2. 先合基础模块 — 有依赖关系的任务，控制合并顺序。
  3. pre_merge + post_merge 双保险 — pre_merge 做快速检查，post_merge 跑全量测试。
  4. 利用 AI 辅助合并 — 冲突时优先选 AI 路径，Agent 处理机械性冲突更高效。
  5. 用 GitHub PR 代替本地合并 — 复杂改动通过 m → Create GitHub PR，让 CI 验证后再合。
  6. 利用 lifecycle hooks 自动化 — worktree_created 自动装依赖，pre_merge 自动跑检查。
