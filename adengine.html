3. 广告召回（Retrieval）

从百万级广告库中快速筛选出候选广告。要求：快（<10ms）、全（不漏召回）、准（减少无效候选）。

layers 召回策略

flip_to_back 倒排索引

  • 按用户标签（年龄/性别/兴趣）查倒排表
  • 适合定向条件匹配
  • 延迟极低，内存占用大

scatter_plot 向量检索 (ANN)

  • 用户和广告都编码为向量
  • 用 FAISS / ScaNN 做近似最近邻
  • 适合个性化召回

rule 规则过滤

  • 频次控制、黑名单、已安装过滤
  • 预算耗尽的广告直接跳过
  • 硬性条件，优先级最高

code 倒排索引示例

// 倒排索引：根据用户标签召回匹配广告
class AdIndex {
  // 索引结构：标签 → 广告 ID 列表
  unordered_map<string, vector<AdId>> inverted_index_;

public:
  // 用户有标签 [游戏, 25岁, 男性]
  // 从倒排索引中召回所有定向这些标签的广告
  vector<Ad> retrieve(const User& user, const Context& ctx) {
    unordered_set<AdId> candidates;
    for (const auto& tag : user.tags()) {
      auto it = inverted_index_.find(tag);
      if (it != inverted_index_.end()) {
        candidates.insert(it->second.begin(), it->second.end());
      }
    }
    // 过滤：预算、频次、黑名单...
    return filter(candidates, user, ctx);
  }
};

4. 广告排序（Ranking）

对召回的候选广告打分排序，决定展示哪个。核心公式：

functions
eCPM = bid × pCTR × pCVR × 1000
bid = 广告主出价  |  pCTR = 预估点击率  |  pCVR = 预估转化率

model_training 排序链路

┌──────────┐ ┌──────────┐ ┌──────────┐ │ 粗排 │────▶│ 精排 │────▶│ 重排 │ │ (轻量模型) │ │ (重量模型) │ │ (业务规则) │ │ 候选 500 │ │ 候选 50 │ │ 最终 5~10 │ └──────────┘ └──────────┘ └──────────┘ ~5ms ~20ms ~2ms

smart_toy CTR/CVR 模型演进

阶段模型特点
LR 时代Logistic Regression简单可解释，特征工程重
树模型GBDT + LR自动特征交叉
深度学习DeepFM / DIN / DIEN自动学习特征交互
多任务MMOE / ESMM / PLECTR + CVR 联合建模
大模型Transformer + 用户序列长序列建模，泛化能力强

code 排序核心逻辑

// 排序引擎：计算每个候选广告的 eCPM
class RankingEngine {
  ModelService& ctr_model_;
  ModelService& cvr_model_;

public:
  vector<ScoredAd> rank(const vector<Ad>& candidates,
                       const User& user) {
    vector<ScoredAd> scored;
    for (const auto& ad : candidates) {
      auto features = extractFeatures(user, ad);
      double p_ctr = ctr_model_.predict(features);
      double p_cvr = cvr_model_.predict(features);
      double ecpm = ad.bid() * p_ctr * p_cvr * 1000;
      scored.push_back({ad, ecpm, p_ctr, p_cvr});
    }
    sort(scored.begin(), scored.end(),
         [](auto& a, auto& b) { return a.ecpm > b.ecpm; });
    return scored;
  }
};

5. 竞价引擎（Auction）

多个广告竞争同一个展示位，决定谁赢、付多少钱。

compare_arrows 竞价机制对比

机制全称计费适用场景
GSP Generalized Second Price 赢家付第二名的价格 + 0.01 搜索广告
VCG Vickrey-Clarke-Groves 赢家付对其他人造成的损失 理论最优，计算复杂
oCPM Optimized CPM 按转化目标出价，系统自动优化 信息流广告（主流）
dCPM Dynamic CPM 实时动态出价 程序化广告

code GSP 竞价示例

// GSP 竞价：广义第二价格
struct BidResult {
  AdId winner;
  double winning_price;  // 实际扣费价格
};

BidResult gspAuction(vector<BidEntry>& bids) {
  // 按 eCPM 降序排列
  sort(bids.begin(), bids.end(),
       [](auto& a, auto& b) { return a.ecpm > b.ecpm; });

  // 赢家付第二名的价格 + 0.01
  double price = (bids.size() >= 2)
      ? bids[1].ecpm + 0.01
      : bids[0].bid_floor;

  return {bids[0].ad_id, price};
}

  • 人群：25-35 岁女性
  • 兴趣：游戏、美妆

schedule 排期控制

  • 早 9 点到晚 10 点投放
  • 工作日 / 周末区分
  • 节假日特殊策略

7. 计费引擎（Billing）

实时扣费、防止超投、对账。要求：高并发、强一致、低延迟。

模式全称扣费时机适用场景

CPCCost Per Click每次点击搜索广告

code 实时计费逻辑

// 实时计费：每次展示/点击后扣减广告主余额
class BillingEngine {
  RedisClient& redis_;

public:
  bool charge(AdId id, double cost) {
    // Lua 脚本保证原子性：检查余额 → 扣费 → 记录
    static const char* lua = R"(
      local balance = tonumber(redis.call('GET', KEYS[1]))
      if balance >= tonumber(ARGV[1]) then
        redis.call('DECRBYFLOAT', KEYS[1], ARGV[1])
        redis.call('LPUSH', KEYS[2], ARGV[2])
        return 1
      end
      return 0
    )";

    auto result = redis_.eval(lua,
      {"budget:" + id, "billing_log:" + id},
      {std::to_string(cost), makeLog(id, cost)});

    return result.asInt() == 1;
  }
};
warning
对账机制：实时扣费是估算值，需要离线对账修正。每小时跑一次对账任务，对比实时日志和离线数据，修正差异。
