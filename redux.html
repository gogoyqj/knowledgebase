Redux 是什么？

Redux 是一个可预测的 JavaScript 状态容器，核心思想源自 Elm 架构和 Flux 模式。 它将应用的全部状态存储在一个 单一的 Store 中，通过 纯函数 Reducer 来描述状态变更， 并通过 Action 来描述"发生了什么"。

lightbulb
Redux 的三大原则：单一数据源、State 只读、纯函数修改。这三条约束让状态变更变得可追踪、可回放、可测试。
compare_arrows

三大核心原则

database 单一数据源

整个应用的状态存储在唯一一个 Store 对象树中。这让 SSR、调试、状态持久化变得简单——只需序列化一棵树。

block State 只读

唯一改变 State 的方法是 dispatch 一个 Action。Action 是普通对象，描述"发生了什么"，但不描述"怎么变"。

functions 纯函数修改

Reducer 是纯函数 (state, action) => newState，不产生副作用，不修改原 State，确保可预测性。

const addTodoAction = {
  type: 'todos/add',       // 必须字段：Action 类型
  payload: {              // 可选：携带的数据
    id: 1,
    text: '学习 Redux',
    completed: false
  },
  meta: {},               // 可选：额外信息（如来源、时间戳）
  error: false            // 可选：是否为错误 Action
}

// Action Creator — 创建 Action 的工厂函数
const addTodo = (text) => ({
  type: 'todos/add',
  payload: { id: nextId(), text, completed: false }
})

// Reducer — 纯函数：(state, action) => newState
function todosReducer(state = [], action) {
  switch (action.type) {
    case 'todos/add':
      return [...state, action.payload]   // 不可变更新！
    case 'todos/toggle':
      return state.map(todo =>
        todo.id === action.payload.id
          ? { ...todo, completed: !todo.completed }
          : todo
      )
    default:
      return state                       // 未匹配则原样返回
  }
}

Store 核心 API — 手写实现

Redux Store 的实现极其精简，核心仅约 30 行代码：

function createStore(reducer, enhancer) {
  // 1. 如果传入了 enhancer（中间件），用它增强 createStore
  if (typeof enhancer === 'function') {
    return enhancer(createStore)(reducer)
  }

  let currentState          // 当前状态树
  let listeners = []        // 订阅者列表
  let isDispatching = false // 防止在 reducer 中 dispatch

  // 2. 获取当前状态
  function getState() {
    return currentState
  }

  // 3. 订阅状态变化，返回取消订阅函数
  function subscribe(listener) {
    listeners.push(listener)
    let subscribed = true
    return function unsubscribe() {
      if (!subscribed) return
      subscribed = false
      const idx = listeners.indexOf(listener)
      listeners.splice(idx, 1)
    }
  }

  // 4. 派发 Action — 唯一的状态修改入口
  function dispatch(action) {
    if (typeof action.type === 'undefined') {
      throw new Error('Actions must have a type')
    }
    if (isDispatching) {
      throw new Error('Reducers may not dispatch actions')
    }
    try {
      isDispatching = true
      currentState = reducer(currentState, action) // 纯函数调用
    } finally {
      isDispatching = false
    }
    listeners.forEach(fn => fn())  // 通知所有订阅者
    return action
  }

  // 5. 初始化：dispatch 一个随机 type 来获取初始状态
  dispatch({ type: `@@redux/INIT${Math.random()}` })

  return { getState, subscribe, dispatch }
}
info
关键设计：isDispatching 锁确保 Reducer 中不能再 dispatch，强制保持 Reducer 的纯函数特性。初始 dispatch 的随机 type 用于触发 Reducer 返回默认值。

combineReducers — 状态切片

当应用状态变复杂时，需要将 Reducer 拆分为多个独立的子 Reducer，每个管理自己的状态切片（slice）：

function combineReducers(reducers) {
  const reducerKeys = Object.keys(reducers)

  return function combination(state = {}, action) {
    let hasChanged = false
    const nextState = {}

    for (const key of reducerKeys) {
      const previousStateForKey = state[key]
      const nextStateForKey = reducers[key](previousStateForKey, action)
      nextState[key] = nextStateForKey
      hasChanged = hasChanged || nextStateForKey !== previousStateForKey
    }

    // 只要有任何一个切片引用变了，就返回新对象
    return hasChanged ? nextState : state
  }
}

// 使用示例
const rootReducer = combineReducers({
  todos:    todosReducer,      // state.todos
  filters:  filtersReducer,    // state.filters
  user:     userReducer        // state.user
})

中间件是什么？

Redux 中间件是位于 dispatch(action) 和 reducer 之间的扩展层。 它提供的是 dispatch 与 reducer 之间的第三方扩展能力，可以在不修改 store 和 reducer 的前提下， 对 dispatch 行为进行拦截、增强或替换。

lightbulb
核心公式：中间件 = 拦截 dispatch 的函数。它让你在 Action 到达 Reducer 之前执行副作用（异步、日志、路由等），但不改变 Redux 的核心数据流。

中间件签名 — 三层柯里化

Redux 中间件采用 三层柯里化 函数签名，这是理解中间件的关键：

// 中间件的标准签名（三层柯里化）
const myMiddleware = store => next => action => {
  //  ▲                  ▲         ▲
  //  │                  │         └── 第三层：接收到的 Action
  //  │                  └──────────── 第二层：下一个中间件的 dispatch
  //  └─────────────────────────────── 第一层：Store 的 { getState, dispatch }

  console.log('dispatching', action)
  const result = next(action)   // 传递给下一个中间件
  console.log('next state', store.getState())
  return result                  // 返回 dispatch 结果
}

// 拆解来看：
const myMiddleware = (store) => {           // 第一层：注入 store
  return (next) => {                         // 第二层：注入 next dispatch
    return (action) => {                     // 第三层：处理 action
      // 前置逻辑（洋葱的外层）
      const result = next(action)             // 调用下一个中间件
      // 后置逻辑（洋葱的内层返回时）
      return result
    }
  }
}

applyMiddleware — 手写实现

applyMiddleware 是 Redux 的 Store Enhancer，它将多个中间件组合成一个增强版 dispatch：

function applyMiddleware(...middlewares) {
  // 返回一个 Store Enhancer
  return (createStore) => (reducer) => {
    // 1. 创建原始 Store
    const store = createStore(reducer)
    let dispatch = () => {
      throw new Error('Dispatch while constructing')
    }

    // 2. 给中间件提供受限的 store API
    const middlewareAPI = {
      getState: store.getState,
      dispatch: (action, ...args) => dispatch(action, ...args)
    }

    // 3. 柯里化第一层：注入 store
    const chain = middlewares.map(mw => mw(middlewareAPI))

    // 4. 组合中间件：每个中间件的 next 指向下一个
    dispatch = compose(...chain)(store.dispatch)

    return { ...store, dispatch }
  }
}

// compose 函数 — 从右到左组合函数
function compose(...funcs) {
  if (funcs.length === 0) return (arg) => arg
  if (funcs.length === 1) return funcs[0]
  return funcs.reduce((a, b) => (...args) => a(b(...args)))
}

// compose(f, g, h) => (...args) => f(g(h(...args)))
// 执行顺序：h → g → f（从右到左）
// 但在中间件中，最左边的最先被调用
info
为什么 compose 从右到左？ 因为 compose(logger, thunk)(dispatch) 等价于 logger(thunk(dispatch))，thunk 包裹了原始 dispatch，logger 再包裹 thunk，所以 logger 最外层、最先执行。

自定义中间件实战

// ① 错误上报中间件
const crashReporter = store => next => action => {
  try {
    return next(action)
  } catch (err) {
    console.error('🔴 Caught an exception!', err)
    Sentry.captureException(err, {
      extra: { action, state: store.getState() }
    })
    throw err   // 仍然抛出，让其他中间件/调用者知道
  }
}

// ② Action 节流中间件
const throttle = (type, ms) => {
  let lastDispatch = 0
  return store => next => action => {
    if (action.type === type && Date.now() - lastDispatch < ms) {
      return    // 静默丢弃
    }
    lastDispatch = Date.now()
    return next(action)
  }
}

// ③ Action 过滤中间件
const filter = predicate => store => next => action => {
  if (!predicate(action, store.getState())) return
  return next(action)
}

// ④ 批量 dispatch 中间件
const batchMiddleware = store => next => action => {
  if (action.type === 'BATCH' && Array.isArray(action.payload)) {
    action.payload.forEach(a => store.dispatch(a))
    return
  }
  return next(action)
}

redux-thunk 源码

Thunk 中间件的源码极其精简——仅 10 行：

// redux-thunk 源码（v2.x）
function createThunkMiddleware(extraArgument) {
  return ({ dispatch, getState }) => next => action => {
    // 如果 action 是函数，调用它
    if (typeof action === 'function') {
      return action(dispatch, getState, extraArgument)
    }
    // 否则继续传递
    return next(action)
  }
}
const thunk = createThunkMiddleware()
export default thunk

// ────────────────────────────────────
// 使用示例
// ────────────────────────────────────

// 普通 Action Creator（返回对象）
const increment = () => ({ type: 'counter/increment' })

// Thunk Action Creator（返回函数）
const fetchUser = (userId) => {
  return async (dispatch, getState) => {
    dispatch({ type: 'users/fetchStart' })
    try {
      const res = await fetch(`/api/users/${userId}`)
      const data = await res.json()
      dispatch({ type: 'users/fetchSuccess', payload: data })
    } catch (err) {
      dispatch({ type: 'users/fetchError', error: err.message })
    }
  }
}

// 条件 dispatch
const fetchIfNeed = (userId) => (dispatch, getState) => {
  const { users } = getState()
  if (!users[userId]) {
    dispatch(fetchUser(userId))
  }
}

redux-saga 核心概念

Saga 使用 Generator 函数声明式地描述副作用流程，将副作用从 Action Creator 中完全抽离：

import { call, put, takeEvery, takeLatest, select } from 'redux-saga/effects'

// Worker Saga — 执行实际工作
function* fetchUserSaga(action) {
  try {
    const user = yield call(Api.fetchUser, action.payload)  // 声明式调用
    yield put({ type: 'users/fetchSuccess', payload: user })  // dispatch action
  } catch (err) {
    yield put({ type: 'users/fetchError', error: err.message })
  }
}

// Watcher Saga — 监听 Action
function* watchFetchUser() {
  yield takeLatest('users/fetch', fetchUserSaga)
}

// Root Saga — 组合所有 Saga
export default function* rootSaga() {
  yield all([
    watchFetchUser(),
    watchOtherFlow(),
  ])
}

// ── 常用 Effect 说明 ──
// call(fn, ...args)    — 调用函数（可 mock，易测试）
// put(action)          — dispatch 一个 action
// take(pattern)        — 等待匹配的 action
// takeEvery(pattern)   — 每个匹配都 fork（并发）
// takeLatest(pattern)  — 只保留最新的（取消之前的）
// select(selector)     — 获取当前 state
// fork(fn)             — 非阻塞 fork
// cancel(task)         — 取消 fork 的任务
// race({...})          — 竞态（谁先完成用谁的结果）
science
为什么 Saga 易测试？ 因为 call / put 只是创建描述对象（Effect），不会立即执行。测试时只需用 generator.next() 逐行推进，断言 yield 出的 Effect 即可，无需 mock 任何网络请求。

如何选择中间件？

thumb_up redux-thunk

简单异步请求、条件 dispatch、需要快速上手的项目。大多数中小型项目足够。

thumb_up redux-saga

复杂异步流程：竞态、取消、重试、轮询、编排多个异步操作。需要可测试性的场景。

thumb_up RTK Query

纯数据获取场景。内置缓存、乐观更新、轮询、自动重取，无需手写任何异步逻辑。

thumb_up redux-observable

基于 RxJS 的响应式方案。适合事件流密集型场景，如 WebSocket、拖拽、键盘输入。

Redux Toolkit（RTK）

Redux Toolkit 是 Redux 官方推荐的编写 Redux 逻辑的方式，解决了原生 Redux 的三大痛点： 配置过多、需要额外包、样板代码多。 它内部集成了 Immer、Reselect、Redux Thunk 等最佳实践。

lightbulb
Redux 官方文档明确建议：所有 Redux 项目都应使用 Redux Toolkit，不再推荐手写 Action Creator、Reducer 和 Store 配置。

原生 Redux vs Redux Toolkit

close 原生 Redux

  • 手写 Action Types、Creators、Reducer
  • 手动 switch-case 判断类型
  • 手动配置 Store、applyMiddleware
  • 手动处理不可变更新（展开运算符地狱）
  • 需要安装 thunk、devtools 等额外包

  • createSlice 自动生成 Actions + Reducer
  • 直接"修改"state（Immer 不可变更新）
  • configureStore 一键配置（含 devtools）
  • 内置 createAsyncThunk 处理异步
  • 内置 RTK Query 数据获取方案

createSlice — 核心 API

import { createSlice } from '@reduxjs/toolkit'

const todosSlice = createSlice({
  name: 'todos',                    // slice 名称（action type 前缀）
  initialState: [],                 // 初始状态
  reducers: {
    // ✨ 直接"修改" state！Immer 会在背后生成不可变更新
    addTodo(state, action) {
      state.push(action.payload)    // 看起来是 mutation，实际是 immutable
    },
    toggleTodo(state, action) {
      const todo = state.find(t => t.id === action.payload)
      if (todo) todo.completed = !todo.completed
    },
    removeTodo: {
      reducer(state, action) {
        return state.filter(t => t.id !== action.payload)
      },
      prepare(id) {                 // 自定义 action payload
        return { payload: id, meta: { timestamp: Date.now() } }
      }
    }
  }
})

// 自动生成的 Action Creators
export const { addTodo, toggleTodo, removeTodo } = todosSlice.actions

// 自动生成的 Reducer
export default todosSlice.reducer

// 生成的 Action：
// { type: 'todos/addTodo', payload: {...} }
// { type: 'todos/toggleTodo', payload: 1 }
// { type: 'todos/removeTodo', payload: 2, meta: { timestamp: ... } }

createAsyncThunk — 异步 Action

import { createSlice, createAsyncThunk } from '@reduxjs/toolkit'

// 创建异步 thunk
export const fetchUser = createAsyncThunk(
  'users/fetch',                  // action type 前缀
  async (userId, { rejectWithValue }) => {
    try {
      const res = await fetch(`/api/users/${userId}`)
      if (!res.ok) throw new Error(res.statusText)
      return await res.json()        // 自动 dispatch fulfilled
    } catch (err) {
      return rejectWithValue(err.message)  // 自动 dispatch rejected
    }
  }
)

// 在 slice 中处理异步状态
const usersSlice = createSlice({
  name: 'users',
  initialState: {
    entity: null,
    loading: 'idle',       // 'idle' | 'pending' | 'succeeded' | 'failed'
    error: null,
  },
  reducers: {},
  // extraReducers 处理外部 action（如 createAsyncThunk 自动生成的）
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => {
        state.loading = 'pending'
      })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.loading = 'succeeded'
        state.entity = action.payload
      })
      .addCase(fetchUser.rejected, (state, action) => {
        state.loading = 'failed'
        state.error = action.payload
      })
  },
})

// 自动 dispatch 三个 action：
// users/fetch/pending   — 请求开始
// users/fetch/fulfilled — 请求成功
// users/fetch/rejected  — 请求失败

RTK Query — 终极数据获取方案

RTK Query 是 Redux Toolkit 内置的数据获取和缓存方案，完全消除了手写 thunk 和状态管理的需要：

import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react'

export const apiSlice = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Todos', 'Users'],    // 缓存标签（用于自动重取）
  endpoints: (builder) => ({
    // 查询（自动缓存）
    getTodos: builder.query({
      query: () => '/todos',
      providesTags: ['Todos'],      // 提供缓存标签
      transformResponse: (res) => res.data,
    }),
    // 变更（自动重取）
    addTodo: builder.mutation({
      query: (newTodo) => ({
        url: '/todos',
        method: 'POST',
        body: newTodo,
      }),
      invalidatesTags: ['Todos'],  // 触发重取 getTodos
    }),
  }),
})

// 自动生成 Hooks：
export const { useGetTodosQuery, useAddTodoMutation } = apiSlice

// 在组件中使用 — 一切自动化
function TodoList() {
  const { data: todos, isLoading, error } = useGetTodosQuery()
  const [addTodo] = useAddTodoMutation()

  if (isLoading) return '加载中...'
  return (
    <ul>
      {todos.map(t => <li key={t.id}>{t.text}</li>)}
      <button onClick={() => addTodo({ text: '新的' })}>添加</button>
    </ul>
  )
}

cached 自动缓存

相同参数的查询自动复用缓存，避免重复请求。支持 refetchOnMountOrArgChange 策略。

autorenew 自动重取

通过 Tag 机制，mutation 成功后自动重取关联的 query，保持数据一致性。

sync 乐观更新

onQueryStarted 支持在请求完成前先更新 UI，失败时自动回滚。

poll 轮询 & 预取

pollingInterval 自动轮询；prefetch 在 hover 时预取数据。

checklist

现代 Redux 最佳实践清单

  • 始终使用 Redux Toolkit — 不再手写原生 Redux 样板代码
  • 用 createSlice — 自动生成 actions + reducer + immer 支持
  • 数据获取首选 RTK Query — 只有复杂异步流才需要 thunk/saga
  • 把逻辑放在 slice 中 — reducer 就是业务逻辑，不要放到组件里
  • 用 TypeScript — RTK 完美支持 TS，自动生成 action 类型
  • 按功能组织目录 — features/todos/todosSlice.ts，而非按类型
  • 不要在 reducer 中写异步逻辑 — 副作用放到 thunk/RTK Query/saga 中
  • 避免嵌套状态 — 使用 createEntityAdapter 管理规范化数据
