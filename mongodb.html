MongoDB 分片与索引策略

多项目接入的海量埋点数据写入场景下，如何设计 Collection Schema、选择 Shard Key、构建索引，实现项目级数据隔离、高吞吐写入与高效聚合查询的平衡。

1. 数据特征分析

埋点数据有几个显著特征，直接决定了存储和分片策略：

特征描述影响
写入密集 QPS 可达 10w+，以 insert 为主 Shard Key 必须分散写入热点
时序性强 每条记录携带时间戳，按时间递增 单调递增 key 会导致热点 shard
文档结构统一 事件类型固定，字段可预测 适合 schema validation + 固定索引
查询以聚合为主 PV/UV 统计、漏斗分析、时间趋势 索引需覆盖 $match + $group 路径
数据可过期 通常保留 90 天 ~ 1 年 可用 TTL Index 自动清理

2. Collection Schema 设计

code events 集合文档结构
BSON { "_id": ObjectId("..."), "project_id": "proj_shop", // 项目标识（多租户隔离） "event_type": "click", // "pv" | "uv" | "click" | "expose" | "custom" "page": "/home", // 页面路径 "element_id": "btn_submit", // 点击元素标识（click 事件用） "user_id": "u_abc123", // 登录用户 ID（可选） "anonymous_id": "did_xyz789", // 设备指纹 / cookie ID "session_id": "sess_001", // 会话 ID "ts": ISODate("2026-08-31T10:30:00Z"), // 事件时间戳 "date": "2026-08-31", // 日期分区键（字符串，按天） "platform": "web", // "web" | "ios" | "android" | "miniapp" "channel": "organic", // 渠道来源 "extra": { // 业务自定义字段 "ab_group": "B", "duration": 12500 } }
lightbulb
为什么加 date 字段？
MongoDB 的日期类型不适合直接做 Shard Key（精度太高导致 chunk 过多）。用 "2026-08-31" 字符串作为日期分区键，既可以作为复合 Shard Key 的一部分，也方便按天查询时精确匹配。
lightbulb
为什么加 project_id 字段？
多项目接入后，查询几乎总是 { project_id, date, page } 组合过滤。将 project_id 放入文档和 Shard Key 前缀，可以让 mongos 按项目精准路由到目标 shard，避免跨 shard 的 scatter-gather。同时实现了租户级数据物理隔离。

3. Shard Key 选择（核心决策）

Shard Key 一旦选定不可更改，它决定了数据如何分布在各 shard 上。选错 key 会导致写热点或查询低效。

compare 候选方案对比
方案 Shard Key 写入分布 查询效率 推荐度
A. _id { _id: "hashed" } ✅ 均匀（ObjectId 已含随机性） ❌ 无法按时间/页面路由 ⚠ 谨慎
B. 纯时间戳 { ts: 1 } ❌ 严重热点（单调递增） ✅ 范围查询快 ✗ 不推荐
C. hashed(event_type) { event_type: "hashed" } ❌ 基数太低（仅几种事件） ❌ 无法按时间路由 ✗ 不推荐
D. date + event_type { date: 1, event_type: 1 } ⚠ 按天分散，单天内集中 ✅ 按天查询极快 ⚠ 可用
E. hashed(anonymous_id) { anonymous_id: "hashed" } ✅ 高基数，均匀分散 ⚠ 按时间查询需 scatter-gather ★ 推荐
F. { date, hashed(anonymous_id) } { date: 1, anonymous_id: "hashed" } ✅ 按天 + 用户双重分散 ✅ 按天路由 + 用户聚合 ★ 推荐
G. { project_id, date, hashed(anonymous_id) } { project_id: 1, date: 1, anonymous_id: "hashed" } ✅ 项目 + 天 + 用户三重分散 ✅ 按项目+天精准路由 ★ 多项目最佳
star 多项目最佳：三字段复合 Shard Key
Shard Key { "project_id": 1, "date": 1, "anonymous_id": "hashed" }

第一维度 project_id：路由前缀，db.events.find({ project_id: "proj_shop" }) 直接命中该项目所在的 shard，不同项目数据物理隔离。

第二维度 date：同一项目内按天分区，{ project_id, date } 组合查询可精准路由到单个 shard。

第三维度 anonymous_id: hashed：同项目同天内，哈希分散写入，消除热点。

star_half 单项目备选：两字段 Shard Key
Shard Key { "date": 1, "anonymous_id": "hashed" }

如果只有一个项目接入，可以用之前的两字段方案。但一旦多项目，按 project_id 查询会变成 scatter-gather（命中所有 shard），不推荐。

route MongoDB 复合 Shard Key 路由原理

MongoDB 对复合 Shard Key 使用前缀匹配路由：查询条件覆盖的前缀字段越多，命中的 shard 越少。

查询条件 命中的 shard 是否精准路由
{ project_id: "A" } 项目 A 的数据所在 shard ✅ 按项目路由
{ project_id: "A", date: "2026-08-31" } 项目 A 当天数据所在 shard ✅ 精准路由
{ project_id: "A", date: "2026-08-31", page: "/home" } 同上（page 不在 shard key 中） ✅ 精准路由 + 索引过滤
{ date: "2026-08-31" }（不带 project_id） 所有 shard ❌ scatter-gather
lightbulb
结论：查询时务必带上 project_id，否则前缀匹配失效，退化为全 shard 扫描。前端 SDK 上报时自动注入 project_id，查询接口强制要求该参数。
warning
为什么不用 event_type 作为 Shard Key？
埋点事件类型通常只有 5~10 种（pv、uv、click、expose…），基数太低。MongoDB 要求 Shard Key 的 cardinality 足够高，否则会导致 jumbo chunk（单个 chunk 数据量过大，无法迁移）。
warning
为什么不用单独的 project_id 做 Shard Key？
project_id 基数太低（通常几十到几百个项目），单独使用会导致 chunk 数量受限，无法充分利用多 shard 并行写入。必须搭配高基数字段（如 anonymous_id: hashed）作为后缀。

4. 索引策略

rule 核心原则

埋点场景以写入为主，索引不宜过多（每个索引都会拖慢 insert）。只建查询真正用到的索引。

Index Definitions // 1. TTL 索引 — 自动过期清理（保留 180 天） db.events.createIndex( { "ts": 1 }, { expireAfterSeconds: 15552000 } // 180 * 24 * 3600 ) // 2. 核心聚合：项目 + 天 + 事件类型 db.events.createIndex( { "project_id": 1, "date": 1, "event_type": 1, "ts": 1 } ) // 3. 按项目 + 页面维度统计 db.events.createIndex( { "project_id": 1, "date": 1, "page": 1, "event_type": 1 } ) // 4. 按用户维度查行为序列（漏斗分析） db.events.createIndex( { "project_id": 1, "anonymous_id": 1, "ts": 1 } ) // 5. UV 去重查询（按项目 + 天 + 用户） db.events.createIndex( { "project_id": 1, "date": 1, "anonymous_id": 1, "event_type": 1 } )
query_stats PV 查询
db.events.aggregate([ { $match: { project_id: "proj_shop", date: "2026-08-31", event_type: "pv" }}, { $group: { _id: "$page", pv: { $sum: 1 } }} ]) // 命中索引 #2，精准路由
person UV 查询
db.events.aggregate([ { $match: { project_id: "proj_shop", date: "2026-08-31", event_type: "pv" }}, { $group: { _id: "$page", uv: { $addToSet: "$anonymous_id" } }}, { $project: { uv: { $size: "$uv" } }} ]) // 命中索引 #5
ads_click 点击热力图
db.events.aggregate([ { $match: { project_id: "proj_shop", date: "2026-08-31", event_type: "click", page: "/home" }}, { $group: { _id: "$element_id", clicks: { $sum: 1 } }}, { $sort: { clicks: -1 }} ]) // 命中索引 #3

7. 进阶：UV 精确去重方案

memory 方案 A：$addToSet 精确去重
Aggregation db.events.aggregate([ { $match: { project_id: "proj_shop", date: "2026-08-31", event_type: "pv" } }, { $group: { _id: { page: "$page" }, pv: { $sum: 1 }, unique_users: { $addToSet: "$anonymous_id" } }}, { $project: { page: "$_id.page", pv: 1, uv: { $size: "$unique_users" } }} ])

✓ 优点

  • 结果完全精确
  • 无需额外组件
  • 适合数据量 < 100w / 天

✗ 缺点

  • $addToSet 内存占用大
  • 超大集合会触发 100MB 限制
  • 需要 allowDiskUse: true
memory 方案 B：MongoDB 5.0+ $countAccumulator
Aggregation // MongoDB 7.0+ 支持 $percentile / $median // 对于 UV 去重，可以预先在写入时做去重 // 写入端去重：用 upsert 保证同一用户同天只写一条 db.events_daily.updateOne( { project_id: pid, anonymous_id: uid, date: today, event_type: "pv" }, { $inc: { pv_count: 1 }, $setOnInsert: { first_seen: now, pages: [] }, $addToSet: { pages: page } }, { upsert: true } ) // 查询 UV：直接 countDocuments db.events_daily.countDocuments({ project_id: "proj_shop", date: "2026-08-31", event_type: "pv" })
lightbulb
核心思路：将去重压力从查询端转移到写入端。写入时用 updateOne + upsert 保证同一用户同天同一事件类型只有一条记录，查询时直接 count 即可得到 UV。
memory 方案 C：Redis HyperLogLog 实时去重
Redis // 实时 UV 统计，精确度 0.81% 误差 PFADD "uv:proj_shop:2026-08-31:/home" "user_abc123" PFCOUNT "uv:proj_shop:2026-08-31:/home" // 按小时统计 PFADD "uv:proj_shop:2026-08-31:10:/home" "user_abc123" // 合并多天 PFMERGE "uv:proj_shop:2026-08:week1" "uv:proj_shop:2026-08-31:/home" "uv:proj_shop:2026-08-30:/home"

✓ 优点

  • 每个 key 仅占 12KB
  • 实时查询，毫秒级
  • 支持跨天/跨页合并

✗ 缺点

  • 0.81% 标准误差
  • 需要额外维护 Redis
  • 不支持下钻（看不了具体用户列表）

checklist 方案总结

  • Shard Key：{ project_id: 1, date: 1, anonymous_id: "hashed" } — 项目隔离 + 按天分区 + 用户哈希分散写入
  • 索引：5 个索引均以 project_id 为前缀，覆盖 TTL / 按天聚合 / 按页统计 / 用户行为序列 / UV 去重
  • 查询规则：所有查询必须带 project_id，否则退化为 scatter-gather
  • 写入：Kafka 削峰 + bulkWrite 无序批量 + w:1 j:false 弱持久化
  • UV 去重：小规模用 $addToSet，大规模用写入端 upsert 预去重，实时看板用 Redis HLL
  • 数据保留：TTL Index 自动清理 180 天前数据，热数据用 project_id + date 快速定位
