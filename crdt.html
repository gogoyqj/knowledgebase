CRDT 基础概念
Conflict-free Replicated Data Types

lightbulb 什么是 CRDT？

CRDT（无冲突复制数据类型）是一种特殊的数据结构，它能够在分布式系统中实现 无需协调的最终一致性。多个节点可以独立、并发地修改数据，然后自动合并， 且保证所有节点最终达到相同的状态。

check_circle 核心优势

无需中央协调器、无需锁机制、无需复杂的冲突解决算法，数据自动收敛到一致状态。

rule 核心数学性质

CRDT 的正确性建立在以下数学性质之上：

交换律 Commutativity
a ∘ b = b ∘ a
操作的执行顺序不影响结果
结合律 Associativity
(a ∘ b) ∘ c = a ∘ (b ∘ c)
操作的分组方式不影响结果
幂等性 Idempotency
a ∘ a = a
重复执行同一操作不产生副作用
单调性 Monotonicity
状态只能"增长"，不会回退
保证最终收敛

calculate G-Counter 工作原理

G-Counter 使用向量时钟，每个节点维护自己的计数器：

G-Counter 示例 (3个节点) 节点 A: [5, 0, 0] // A 计数 5 节点 B: [0, 3, 0] // B 计数 3 节点 C: [0, 0, 7] // C 计数 7 合并规则: merge(a, b) = [max(a[i], b[i]) for each i] 合并后: [5, 3, 7] // 总计 = 5 + 3 + 7 = 15 ┌──────────────────────────────────────────────┐ │ A: [5,0,0] ──merge──▶ [5,3,7] ◀──merge── B: [0,3,0] │ │ ▲ │ │ │ │ │ merge│ │ │ │ │ │ C: [0,0,7] │ └──────────────────────────────────────────────┘

text_fields Sequence CRDT（序列 CRDT）

序列 CRDT 是文本编辑的核心。每个字符被赋予一个全局唯一标识符， 通过标识符的偏序关系确定字符顺序，而非依赖数组索引。

info 关键洞察

传统数组使用位置索引 [0, 1, 2, ...]，并发插入会导致索引冲突。 Sequence CRDT 使用唯一 ID，每个字符有固定身份，不受其他插入影响。

Sequence CRDT 字符标识 初始文档: H e l l o 每个字符有唯一 ID: H → (site=A, seq=1, value='H') e → (site=A, seq=2, value='e') l → (site=A, seq=3, value='l') l → (site=A, seq=4, value='l') o → (site=A, seq=5, value='o') 并发插入 "X" 和 "Y" 在位置 2 之后: H e X Y l l o │ │ │ └─ (site=B, seq=1) // B 插入 └───── (site=A, seq=6) // A 插入 排序规则: 先比较 parent ID，再比较 site ID → 所有节点得到相同顺序，无需协调
music_note
Fugue 算法
高性能文本编辑 CRDT · Joseph Gentle & Martin Kleppmann

history 背景与动机

Fugue 是 2023 年由 Joseph Gentle 和 Martin Kleppmann 提出的序列 CRDT 算法， 专为协同文本编辑设计。它解决了早期文本 CRDT 的关键问题：

  • Logoot / LSEQ：使用随机 ID，可能导致排序不一致
  • RGA：并发插入的排序依赖实现细节，行为不可预测
  • YATA (Yjs)：复杂的左右邻居规则，边界情况多
  • Fugue：简洁的数学模型，行为完全可预测

architecture 核心数据结构

Fugue 使用带唯一 ID 的双向链表表示文本序列：

Fugue 数据结构 Character ID = (site_id, sequence_number) • site_id: 节点唯一标识 (UUID 或整数) • sequence_number: 该节点的操作序号 Document = Linked List of Characters ┌─────────────────────────────────────────────────────────────┐ │ │ │ HEAD ◄──▶ (A,1,'H') ◄──▶ (A,2,'e') ◄──▶ (A,3,'l') ◄──▶ ... │ │ │ │ 每个节点存储: │ │ • id: (site, seq) │ │ • value: 字符内容 │ │ • parent_id: 插入位置的参考点 │ │ • is_deleted: 是否已删除 (tombstone) │ │ • left, right: 链表指针 │ │ │ └─────────────────────────────────────────────────────────────┘

compare_arrows 并发插入的处理

当两个用户同时在同一位置插入字符时，Fugue 使用确定性排序规则：

1
找到插入位置
新字符的 parent_id 指向插入点右侧的字符
2
检查并发冲突
如果多个字符有相同的 parent_id，说明是并发插入
3
确定性排序
按 site_id 排序（字典序），site_id 小的排在左边
Fugue 并发插入示例 初始状态: H e l l o 用户 A (site=A): 在 'e' 之后插入 'X' 用户 B (site=B): 在 'e' 之后插入 'Y' 操作: A: insert('X', parent=(A,2)) // parent = 'e' 的 ID B: insert('Y', parent=(A,2)) // 同一个 parent 合并后 (所有节点一致): H e X Y l l o │ │ │ └─ (B,1) // site_id B > A，排在右边 └───── (A,6) // site_id A < B，排在左边 排序规则: 相同 parent 的子节点，按 site_id 字典序排列 → 完全确定性，所有节点结果相同

delete 删除操作与 Tombstone

Fugue 使用 tombstone（墓碑）机制处理删除：

删除操作 删除前: H e l l o 删除 'e' (site=A, seq=2): → 标记 is_deleted = true → 物理上保留在链表中 逻辑视图: H ~~e~~ l l o → H l l o 物理视图: H e(del) l l o // 仍占位 为什么保留 tombstone? → 并发操作可能引用已删除字符作为 parent → 需要保留 ID 以维持因果关系

cleaning_services 垃圾回收 (GC)

长期编辑会产生大量 tombstone，需要垃圾回收：

warning GC 条件

只有当所有节点都确认某个 tombstone 不再被引用时，才能安全删除。 通常通过向量时钟或版本向量追踪全局最小版本来判断。

垃圾回收流程 版本向量: {A: 10, B: 8, C: 12} 全局最小版本: min(10, 8, 12) = 8 规则: seq ≤ 8 的 tombstone 可以安全删除 → 因为所有节点都已处理到 seq=8 删除前: H e(del,seq=2) l x(del,seq=5) l o 删除后: H l x(del,seq=5) l o // seq=2 的被回收

description 文档模型 (Document Model)

ProseMirror 的文档是一棵节点树，而非扁平文本：

ProseMirror 文档树结构 doc ├── heading (level=1) │ └── "Hello World" ├── paragraph │ ├── "This is " │ ├── strong │ │ └── "bold" │ ├── " and " │ ├── em │ │ └── "italic" │ └── " text." └── bullet_list ├── list_item │ └── paragraph │ └── "Item 1" └── list_item └── paragraph └── "Item 2" 节点类型: Block nodes: doc, heading, paragraph, bullet_list, list_item Inline nodes: text (leaf node) Marks: strong, em (装饰，不影响结构)

transform Transform 系统

所有文档修改都通过 Step（步骤）进行，保证可追溯和可逆：

// ProseMirror Transform 示例 import { EditorState } from 'prosemirror-state' import { Transform } from 'prosemirror-transform' // 创建 transform const tr = new Transform(state.doc) // 应用步骤 tr.insert(pos, schema.text('Hello')) tr.delete(from, to) tr.replaceWith(from, to, newNode) // 每个 step 都是可逆的 const inverted = step.invert() // 应用到状态 const newState = state.apply(tr)

sync 数据流

1
用户输入
用户在 ProseMirror EditorView 中输入字符，触发 DOM 事件
2
ProseMirror Transform
ProseMirror 创建 Step（如 ReplaceStep），更新本地 EditorState
3
CRDT 操作转换
Collab Plugin 拦截 Step，转换为 CRDT 操作（如 Fugue insert）
4
本地应用
CRDT 操作应用到本地 Fugue 文档，生成唯一操作 ID
5
网络同步
操作通过 WebSocket 发送到服务器，服务器广播给其他客户端
6
远程合并
收到远程操作后，CRDT 自动合并（无需冲突解决），更新本地文档
7
视图更新
从 CRDT 文档生成新的 ProseMirror Document，更新 EditorView

// ProseMirror ↔ Fugue 适配器伪代码 class FugueAdapter { constructor(schema) { this.fugueDoc = new FugueDocument() this.schema = schema } // ProseMirror Step → Fugue 操作 stepToOps(step) { if (step instanceof ReplaceStep) { const ops = [] // 删除范围内的字符 for (const pos of step.deletedRange) { ops.push(new FugueDelete(pos.id)) } // 插入新字符 for (const char of step.inserted) { ops.push(new FugueInsert(char, step.pos)) } return ops } } // Fugue 文档 → ProseMirror Document toProseMirrorDoc() { const text = this.fugueDoc.toString() // 解析文本为 ProseMirror 节点树 return this.schema.nodeFromJSON( parseText(text, this.schema) ) } // 应用远程操作 applyRemote(ops) { for (const op of ops) { this.fugueDoc.apply(op) } // 触发 ProseMirror 更新 return this.toProseMirrorDoc() } }

layers 富文本的挑战

纯文本 CRDT 只需处理字符序列，但富文本还需处理：

Marks（标记）
粗体、斜体等
需要独立的 CRDT 追踪
使用 LWW-Register 或 OR-Set
Block Structure（块结构）
段落、标题、列表等
需要层次化 CRDT
使用 Tree CRDT 或嵌套 OR-Set
Attributes（属性）
链接、图片 src 等
使用 LWW-Map
最后写入胜出
Cursor Positions（光标）
多用户光标位置
使用 Awareness Protocol
实时同步但不持久化
