App Router 架构总览

Next.js 13+ 引入的 App Router 基于 React Server Components (RSC) 构建，采用app/目录约定式路由，实现了服务端与客户端组件的混合渲染。

Server Components vs Client Components

App Router 的核心设计是 组件边界 —— 通过 'use client' 指令划分运行环境。

dns Server Components (默认)

  • 在服务器上渲染，零客户端 JS
  • 可直接 async/await 访问数据库
  • 不可使用 useState / useEffect
  • 可导入其他 Server 或 Client 组件
  • 适合：数据获取、SEO 内容、敏感逻辑

smartphone Client Components

  • 声明 'use client' 后在浏览器运行
  • 可使用所有 React Hooks 和浏览器 API
  • 仍可在服务端预渲染 (SSR)
  • 不能直接导入 Server Component
  • 适合：交互、事件监听、浏览器 API
// app/page.tsx — 默认是 Server Component
import { db } from '@/lib/db'
import ClientButton from './ClientButton'

export default async function Page() {
  const posts = await db.post.findMany()
  return (
    <div>
      {posts.map(p => <article key={p.id}>{p.title}</article>)}
      <ClientButton />  {/* 交互部分 */}
    </div>
  )
}
// app/ClientButton.tsx
'use client'
import { useState } from 'react'

export default function ClientButton() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>
}
lightbulb
关键原则：将 Client Component 尽量推到组件树的叶子节点，最大化 Server Component 的比例，从而减少客户端 JS 体积。

文件系统约定

App Router 使用特殊的文件名约定来定义路由行为：

description page.tsx

定义路由的可访问页面。没有 page.tsx 的目录不是路由。

web_asset layout.tsx

共享布局，在导航间保持状态，不重新挂载。支持嵌套。

hourglass_top loading.tsx

自动 Suspense 边界，在子组件加载时显示即时 UI。

error error.tsx

错误边界（必须是 Client Component），捕获子级异常。

find_replace not-found.tsx

处理 notFound() 抛出或 404 的 UI。

template template.tsx

类似 layout，但每次导航重新挂载实例（适合动画/焦点）。

settings default.tsx

Parallel Routes 的回退 UI，当插槽未匹配时渲染。

api route.ts

API 路由端点，定义 GET/POST/PUT 等处理器。

call_split

高级路由模式

Parallel Routes (平行路由)

使用 @slot 命名的目录，在同一页面同时渲染多个独立页面段。适合 Dashboard 等多面板布局。

// app/layout.tsx
export default function Layout({ children, analytics, team }) {
  return (
    <div>
      {children}    {/* app/page.tsx */}
      {analytics}   {/* app/@analytics/page.tsx */}
      {team}        {/* app/@team/page.tsx */}
    </div>
  )
}

Intercepting Routes (拦截路由)

通过 (.) / (..) / (...) 约定拦截同级 / 上级 / 根级路由，常用于模态框场景。

// app/feed/(.)photo/[id]/page.tsx  → 拦截 /feed/photo/[id]
// 在 /feed 页面内弹出模态框显示照片详情
// 直接访问 /photo/123 则显示完整页面

四层缓存架构

Next.js 的缓存系统由四层组成，每层服务于不同的场景：

┌─────────────────────────────────────────────────────────┐ │ ④ Router Cache (客户端) │ │ 位置: 浏览器内存 │ │ 对象: RSC Payload (Flight 数据) │ │ 生命周期: Session → 5min(static) / 30min(dynamic) │ │ 作用: 前进/后退 instant, prefetch 路由段 │ ├─────────────────────────────────────────────────────────┤ │ ③ Full Route Cache (服务端) │ │ 位置: CDN / 服务端持久化 │ │ 对象: 整个路由段的渲染结果 (HTML + RSC Payload) │ │ 生命周期: 直到重新部署或 revalidate │ │ 作用: 静态路由的零计算响应 │ │ ⚠️ Next.js 16: 被 Segment Cache 取代 │ ├─────────────────────────────────────────────────────────┤ │ ② Data Cache (服务端) │ │ 位置: 服务端持久化存储 │ │ 对象: fetch() 响应 / 第三方库通过 unstable_cache │ │ 生命周期: 跨请求、跨部署持久 │ │ 作用: 避免重复数据请求 │ ├─────────────────────────────────────────────────────────┤ │ ① Request Memoization (请求级) │ │ 位置: 单次请求的 React 渲染周期内 │ │ 对象: 相同参数的 fetch() 调用 │ │ 生命周期: 单次请求 │ │ 作用: 组件树多处 fetch 同一 URL 只发一次 │ └─────────────────────────────────────────────────────────┘

Segment Cache 深度解析 (v15.2+)

Segment Cache 是 Next.js 对 Full Route Cache 的重新设计。核心思想：不再缓存整个路由的渲染结果，而是按路由段 (Segment) 粒度缓存。

info
为什么需要 Segment Cache？
Full Route Cache 缓存的是完整路由 —— 当布局嵌套很深时，导航到子路由会重新请求整个页面。Segment Cache 让每个布局段独立缓存，导航时只需获取变化的部分。

Segment 的概念

每个路由段对应 URL 的一层。例如 /dashboard/settings 包含三个段：

/                → Root Layout (layout.tsx)
/dashboard       → Dashboard Layout (app/dashboard/layout.tsx)
/dashboard/settings → Page (app/dashboard/settings/page.tsx)

// 每个段独立缓存为一个 "Segment Entry"
// 包含：RSC Payload + Headers + 生成时间戳

Segment Entry 结构

interface SegmentEntry {
  // 该段的 RSC Payload (React Flight 格式)
  rscPayload: ReadableStream
  // HTTP Headers (包括 revalidation 时间等)
  headers: Headers
  // 该段是否是动态的
  isDynamic: boolean
  // 缓存失效时间
  staleAt: number
}

Segment Cache vs Full Route Cache

block Full Route Cache (旧)

  • 缓存整个路由的渲染结果
  • 导航到子路由 → 重新请求所有父布局
  • 嵌套布局越多，浪费越大
  • 一个 revalidate 影响整条路由链

done_all Segment Cache (新)

  • 按路由段独立缓存
  • 导航时只获取变化的段
  • 父布局可独立于子页面缓存
  • 精细控制每个段的 revalidation

工作流程

用户点击 /dashboard/settings 链接: 1. Client Router 检查 Router Cache (内存) ├─ 命中 → 直接渲染 (instant back/forward) └─ 未命中 ↓ 2. 发起请求到 Server 请求包含: 目标 URL + 当前已缓存的 Segment 列表 3. Server 计算需要哪些 Segment ├─ / layout → 命中 Segment Cache ✓ (跳过) ├─ /dashboard layout → 命中 Segment Cache ✓ (跳过) └─ /dashboard/settings → 未命中 → 重新渲染 ✗ 4. Server 返回: 仅缺失的 Segment 的 RSC Payload 5. Client 合并已有 Segment + 新 Segment → 完整页面

缓存控制 API

Route Segment Config

// app/dashboard/page.tsx

// 方式一：静态配置
export const revalidate = 3600   // ISR: 每小时重新验证
export const dynamic = 'force-static'
export const dynamicParams = true  // 允许动态参数

// 方式二：按需重新验证 (推荐)
import { revalidatePath, revalidateTag } from 'next/cache'

export async function action() {
  // 重新验证整个路径
  revalidatePath('/dashboard')

  // 或按 tag 精确失效
  revalidateTag('posts')
}

// 方式三：使用 cache: 'no-store' 完全动态
const data = await fetch('/api/data', {
  cache: 'no-store'
})

unstable_cache (手动缓存任意函数)

import { unstable_cache } from 'next/cache'

const getCachedPosts = unstable_cache(
  async (userId: string) => {
    return db.post.findMany({ where: { userId } })
  },
  ['posts-by-user'],       // cache key parts
  { tags: ['posts'], revalidate: 3600 }
)

Server Actions (服务端操作)

Server Actions 是 Next.js 14+ 稳定的服务端函数，可直接在 Client 或 Server Component 中调用，无需手动创建 API 端点。

// app/actions.ts
'use server'

import { revalidatePath } from 'next/cache'
import { redirect } from 'next/navigation'

export async function createPost(formData: FormData) {
  const title = formData.get('title') as string

  // 直接操作数据库
  await db.post.create({ data: { title } })

  // 重新验证缓存
  revalidatePath('/posts')
  redirect('/posts')
}

// app/new-post/page.tsx (Server Component 中使用)
export default function NewPost() {
  return (
    <form action={createPost}>
      <input name="title" />
      <button type="submit">发布</button>
    </form>
  )
}
warning
安全注意：Server Actions 通过 POST 请求暴露为端点。务必在函数内部做鉴权和输入校验，不要依赖"隐藏"来保护敏感操作。

渲染策略矩阵

Next.js 支持多种渲染策略，可在路由级别灵活组合：

html Static Rendering (SSG)

构建时预渲染 HTML。最快响应，适合内容不频繁变化的页面。通过 generateStaticParams 预生成动态路由。

update ISR (增量静态再生)

静态页面在后台按 revalidate 间隔重新生成。兼顾速度与新鲜度。Segment Cache 支持段级 revalidation。

dns Dynamic Rendering (SSR)

每次请求在服务端渲染。使用 cookies() / headers() / searchParams 等动态 API 时自动触发。

auto_awesome PPR (部分预渲染)

将页面分为静态壳 + 动态洞。静态部分预渲染并缓存在 CDN，动态部分在请求时流式填充。

auto_awesome

Partial Prerendering (PPR) 深度解析

PPR 是 Next.js 最重要的渲染创新之一。它打破了"整页静态或整页动态"的二元选择：

传统方式 (只能整页选一种): ┌─────────────────────────────┐ │ 整页 Static (SSG) │ ← 全部构建时渲染, 无法个性化 │ 或 │ │ 整页 Dynamic (SSR) │ ← 每次请求都要等全部渲染 └─────────────────────────────┘ PPR (同一页面混合): ┌─────────────────────────────┐ │ ┌───────────────────────┐ │ │ │ Static Shell │ │ ← 构建时预渲染, CDN 缓存 │ │ (Header, Nav, Footer)│ │ 立即返回给用户 │ ├───────────────────────┤ │ │ │ ┌─ Suspense ──────┐ │ │ │ │ │ Dynamic Hole │ │ │ ← 请求时流式填充 │ │ │ (个性化内容) │ │ │ 用户看到 shell 先加载 │ │ │ (购物车/推荐) │ │ │ │ │ └──────────────────┘ │ │ │ └───────────────────────┘ │ └─────────────────────────────┘
// next.config.js — 启用 PPR
const nextConfig = {
  experimental: {
    ppr: 'incremental'  // 逐路由启用
  }
}

// app/dashboard/page.tsx — 选择性启用
export const experimental_ppr = true

import { Suspense } from 'react'

export default function Dashboard() {
  return (
    <div>
      <StaticHeader />          {/* 构建时渲染 */}
      <Suspense fallback={<Skeleton />}>
        <UserRecommendations />  {/* 请求时渲染 */}
      </Suspense>
    </div>
  )
}
check_circle
PPR 的核心优势：用户几乎瞬间看到页面骨架（静态壳），动态内容在获取完成后流式注入。TTFB 接近静态页面，同时保留个性化能力。

Streaming SSR

Next.js 使用 React 18+ 的 Streaming SSR，将 HTML 分块传输：

// 使用 Suspense 定义流式边界
import { Suspense } from 'react'

export default function Page() {
  return (
    <main>
      {/* 这部分立即发送 */}
      <h1>产品页面</h1>

      {/* 这部分准备好后流式发送 */}
      <Suspense fallback={<ProductSkeleton />}>
        <ProductDetails />  {/* async Server Component */}
      </Suspense>

      <Suspense fallback={<ReviewsSkeleton />}>
        <ProductReviews />  {/* 可独立加载 */}
      </Suspense>
    </main>
  )
}

浏览器收到第一个 chunk 后就开始解析和渲染 shell，后续 chunk 到达时替换 Suspense fallback。这比传统 SSR 的"等全部渲染完再返回"要快得多。

Next.js 15 的重大变化

1. 缓存策略反转 — 不再默认缓存一切

这是 15 最具争议的改动。之前 fetch() 默认 cache: 'force-cache'，15 改为 cache: 'no-store' (默认不缓存)。

block Next.js 14 及之前

  • fetch() 默认 强制缓存
  • GET Route Handlers 默认缓存
  • 客户端 Router 默认缓存 30s
  • 开发者经常遇到"为什么数据不更新？"的问题

done_all Next.js 15

  • fetch() 默认 不缓存
  • GET Route Handlers 默认不缓存
  • 客户端 Router 默认不缓存
  • 需要缓存时显式声明

2. 异步请求 API

cookies()、headers()、params、searchParams 全部变为 async：

❌ Next.js 14

const cookieStore = cookies()
const token = cookieStore.get('token')

✅ Next.js 15

const cookieStore = await cookies()
const token = cookieStore.get('token')

这使得 Next.js 可以在渲染开始前收集所有动态依赖，为 PPR 等优化铺路。

3. React 19 全面支持

code use() Hook

在渲染时 resolve Promise，简化异步数据读取。可在条件语句和循环中使用。

forward ref as prop

ref 作为普通 prop 传递，不再需要 forwardRef。

dns Actions (原 useFormState)

表单的 action 属性原生支持，useActionState 替代 useFormState。

text_fields Metadata API

改进的 Metadata 类型，原生支持 <meta charset> 等。

4. Turbopack 成为默认构建器

Turbopack (基于 Rust 的增量计算引擎) 在 15 中成为 next dev 和 next build 的默认选项：

  • 冷启动快 76.7%
  • HMR 快 96.3%
  • 大型应用编译快 45.8%

Next.js 16 的重大改进

1. Segment Cache 稳定化

Segment Cache 从实验变为默认行为。Full Route Cache 被完全取代：

  • 每个路由段独立缓存和失效
  • 导航时只传输变化的段，而非整个页面
  • 支持 Prefetch 策略：'auto' / 'full' / 'viewport'
  • 通过 prefetch={false} 禁用特定链接的预取
// 链接预取策略
import Link from 'next/link'

// 默认: 视口内自动预取静态段
<Link href="/dashboard">Dashboard</Link>

// 完整预取: 包括动态段
<Link href="/dashboard" prefetch="full">Dashboard</Link>

// 禁用预取
<Link href="/heavy-page" prefetch={false}>Heavy</Link>

2. cacheComponents (实验性)

允许在组件级别控制缓存，而非路由段级别：

// 启用实验性功能
// next.config.js
const config = {
  experimental: {
    cacheComponents: true
  }
}

// 组件级缓存标记
'use cache'  // 指令级缓存控制 (实验性)

export default async function ExpensiveComponent() {
  // 此组件的渲染结果会被独立缓存
  const data = await fetchExpensiveData()
  return <div>{data}</div>
}

3. dynamicIO (实验性)

全新的动态渲染模型。使用 'use cache' 和 cacheLife() / cacheTag() 替代旧的 revalidate 数字配置：

import { cacheLife, cacheTag } from 'next/cache'

'use cache'

export default async function CachedPage() {
  // 声明缓存生命周期
  cacheLife('hours')    // 预设: 'seconds' | 'minutes' | 'hours' | 'days'

  // 声明缓存标签 (用于按需失效)
  cacheTag('page-cached')

  const data = await getData()
  return <div>{data}</div>
}

// 按需失效
import { revalidateTag } from 'next/cache'
revalidateTag('page-cached')
lightbulb
dynamicIO 的核心思想：不再让框架猜测哪些请求该缓存，而是让开发者通过 'use cache' 指令显式声明。没有标记的一律动态执行，消除了"默认缓存一切"的困惑。

4. Node.js 中间件

16 之前中间件只能在 Edge Runtime 运行，16 支持 Node.js Runtime：

// middleware.ts
export const runtime = 'nodejs'  // 新增: 使用 Node.js 运行时

export function middleware(request: NextRequest) {
  // 现在可以使用 Node.js API
  // 例如: crypto, fs, 数据库驱动等
  const session = verifySession(request.cookies)
  if (!session) return redirect('/login')
}

5. unstable_cache → cache()

API 重命名和改进：

// 旧: unstable_cache
import { unstable_cache } from 'next/cache'
const fn = unstable_cache(handler, keys, options)

// 新: cache() (Next.js 16)
import { cache } from 'next/cache'
const fn = cache(handler, keys, options)

warning
渐进式迁移：v16 的实验性功能（cacheComponents、dynamicIO）可通过 next.config.js 逐个开启，无需一次性全部迁移。

  3. 启用 PPR：在适合的页面设置 experimental_ppr = true
  4. 尝试 Segment Cache：在 v15.2+ 中启用，观察缓存粒度变化
  5. 评估 dynamicIO：在新项目中试验 'use cache' 指令
  6. 利用 Node.js 中间件：将依赖 Node API 的中间件从 Edge 迁移
