React Native C++ Plugin 开发指南

从零构建一个使用 C++ 实现核心逻辑的 React Native 原生模块。涵盖 JSI、Bridge、Expo Modules、Nitro Modules 四种方案。

1. React Native 工作原理

核心思想：JavaScript 驱动原生 UI

React Native 的本质是用 JavaScript 编写业务逻辑，但渲染的是真正的原生控件（不是 WebView）。它通过一个桥接层让 JS 和 Native 互相通信。

三线程模型

┌─────────────────────────────────────────────────────────────────────────┐ │ React Native Thread Model │ │ │ │ ┌──────────────────┐ ┌──────────────────┐ ┌────────────────────┐ │ │ │ JS Thread │ │ Native Thread │ │ Shadow Thread │ │ │ │ │ │ │ │ (Yoga Layout) │ │ │ │ • React 逻辑 │ │ • 原生 UI 渲染 │ │ • Flexbox 布局计算│ │ │ │ • 业务代码 │ │ • 原生模块调用 │ │ • 样式解析 │ │ │ │ • 状态管理 │ │ • 事件处理 │ │ │ │ │ │ • JSI 调用 │ │ • 绘制到屏幕 │ │ │ │ │ └────────┬─────────┘ └────────┬─────────┘ └────────┬───────────┘ │ │ │ │ │ │ │ └──────────────────────┼──────────────────────┘ │ │ Communication Layer │ │ (Bridge / JSI / Fabric) │ └─────────────────────────────────────────────────────────────────────────┘
  • JS Thread：运行 Hermes 或 JavaScriptCore 引擎，执行 React 组件树的渲染逻辑、状态更新、事件回调
  • Native Thread（UI Thread）：负责原生 View 的创建、布局、绘制，以及触摸事件的分发
  • Shadow Thread：运行 Yoga（Facebook 的跨平台 Flexbox 引擎），计算布局树，将 JS 的 StyleSheet 转换为绝对坐标

渲染流程

JS: setState() → Virtual DOM Diff → Shadow Tree 布局 → Native View 更新 → 屏幕渲染
  1. JS 侧：React 执行 render，生成 Virtual DOM，diff 出变化
  2. 序列化传输：将 UI 操作指令序列化（旧架构 JSON，新架构 JSI 直传）
  3. Shadow Tree：Yoga 引擎计算 Flexbox 布局，得出每个 View 的位置和尺寸
  4. Native 侧：根据布局结果创建/更新真正的原生 UIView（iOS）或 ViewGroup（Android）
  5. 事件回传：用户触摸 → Native 捕获 → 序列化为事件 → JS 处理回调

新架构四大支柱

组件替代作用
JSI Bridge C++ 直调，替代 JSON 序列化的异步桥接
Fabric Old Renderer 新渲染器，支持同步渲染、并发特性、优先级调度
TurboModules NativeModules 懒加载原生模块，按需初始化，类型安全
Codegen 手动类型桥接 从 TypeScript/Flow 自动生成 C++/ObjC/Kotlin 类型
┌─────────────────────────────────────────────────────────────────────┐ │ React Native 新架构全景 │ │ │ │ JavaScript │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ React Components → Hermes/JSC Engine │ │ │ └────────────────────────────┬───────────────────────────────┘ │ │ │ JSI (C++ 直调，无 Bridge) │ │ C++ Core ▼ │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ ┌─────────────┐ ┌──────────────┐ ┌──────────────────┐ │ │ │ │ │ Fabric │ │ TurboModules │ │ Codegen │ │ │ │ │ │ (渲染器) │ │ (原生模块) │ │ (类型生成) │ │ │ │ │ └──────┬──────┘ └──────┬───────┘ └──────────────────┘ │ │ │ └─────────┼────────────────┼─────────────────────────────────┘ │ │ │ │ │ │ Platform ▼ ▼ │ │ ┌──────────────────┐ ┌──────────────────┐ │ │ │ iOS (UIKit) │ │ Android (View) │ │ │ │ UIView/ViewGroup│ │ ViewGroup/View │ │ │ └──────────────────┘ └──────────────────┘ │ └─────────────────────────────────────────────────────────────────────┘
关键区别：旧架构中 JS 和 Native 通过异步 Bridge（JSON 队列）通信，每帧最多传递一次消息。新架构通过 JSI 让 JS 直接调用 C++ 对象，实现同步、零拷贝通信，这是性能飞跃的关键。

2. React Native 启动过程

从用户点击 App 图标到第一个像素渲染到屏幕上，React Native 经历以下阶段：

总览

┌─────────────────────────────────────────────────────────────────────────┐ │ React Native Startup Sequence │ │ │ │ ① Native 启动 ② JS 引擎初始化 ③ JS Bundle 加载执行 │ │ ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐ │ │ │ Application │────▶│ Hermes/JSC │────▶│ require('AppRegistry')│ │ │ │ onCreate │ │ Runtime 创建 │ │ AppRegistry │ │ │ │ │ │ │ │ .registerComponent() │ │ │ └──────────────┘ └──────────────┘ └──────────┬───────────┘ │ │ │ │ │ ⑤ 首帧渲染 ④ React 渲染 │ │ │ ┌──────────────┐ ┌──────────────┐ │ │ │ │ 原生 View │◀────│ Shadow Tree │◀──────────────┘ │ │ │ 显示到屏幕 │ │ 布局计算 │ AppRegistry │ │ │ │ │ │ .runApplication() │ │ └──────────────┘ └──────────────┘ │ └─────────────────────────────────────────────────────────────────────────┘

阶段 1：Native 容器启动

平台原生代码首先启动，创建承载 React Native 的容器。

// iOS — AppDelegate.swift
func application(_ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {

    let bridge = RCTBridge(delegate: self, launchOptions: launchOptions)
    let rootView = RCTRootView(bridge: bridge, moduleName: "MyApp", initialProperties: nil)
    // rootView 就是 RN 在原生侧的入口 View
}
// Android — MainApplication.kt
class MainApplication : Application(), ReactApplication {
    override val reactHost: ReactHost
        get() = ReactHost(this, reactNativeHost)

    override val reactNativeHost = object : ReactNativeHost(this) {
        override fun getPackages() = listOf(MainReactPackage())
        override fun getJSMainModuleName() = "index"
        override fun getBundleAssetName() = "index.android.bundle"
    }
}

这个阶段完成的事情：

  • 创建 RCTBridge（iOS）/ ReactInstanceManager（Android），它是 JS 与 Native 的核心协调器
  • 注册所有 Native Modules（原生模块）和 View Managers（原生组件）
  • 创建 RCTRootView，它是 React 组件树挂载的原生根视图

阶段 2：JS 引擎初始化

Native 容器就绪后，创建 JavaScript 运行时：

  • Hermes（默认）：Facebook 专为 React Native 打造的 JS 引擎，支持字节码预编译，启动更快、内存占用更低
  • JavaScriptCore（JSC）：Apple 的 WebKit JS 引擎，旧版本 RN 的默认引擎
  • V8：Chrome 的 JS 引擎，部分场景可选
Hermes 优势：将 JS 源码预编译为 Hermes 字节码（.hbc），跳过解析和编译阶段，启动时间减少约 30-40%。

阶段 3：JS Bundle 加载与执行

引擎初始化完成后，加载并执行 JavaScript 代码：

定位 Bundle → 加载到内存 → 执行入口文件 → 注册 Root Component 
// index.js — JS 入口文件
import { AppRegistry } from 'react-native';
import App from './App';

// 注册根组件，名称必须与 Native 侧的 moduleName 一致
AppRegistry.registerComponent('MyApp', () => App);
Bundle 来源场景说明
Assets（打包内置） Release 构建 Bundle 打包进 App，从 assets 目录读取
Dev Server Debug 构建 从 Metro Bundler（localhost:8081）热加载
CodePush / OTA 热更新 运行时从远端下载新 Bundle

阶段 4：React 渲染与布局

JS Bundle 执行后，React 开始工作：

// AppRegistry.runApplication() 内部流程：

1. 调用 AppRegistry.runApplication('MyApp', { rootTag })
     ↓
2. React 渲染根组件 <App />
     ↓
3. 生成 Fiber Tree（Virtual DOM）
     ↓
4. Yoga 引擎计算 Flexbox 布局 → Shadow Tree
     ↓
5. Fabric（新）/ 旧渲染器 将 Shadow Tree 映射为原生 View 指令
     ↓
6. Native 侧创建真正的 UIView / ViewGroup

阶段 5：首帧上屏

原生 View 创建并布局完成后，系统 GPU 合成渲染，第一个画面显示到屏幕上。从这里开始，App 进入正常的事件循环：

用户触摸 → Native 捕获事件 → JS 回调处理 → setState 触发重渲染 → UI 更新

启动性能关键指标

指标含义优化手段
TTI（Time To Interactive） 从点击图标到 App 可交互 Hermes 字节码、Bundle 拆分、懒加载
Bundle Size JS Bundle 大小 Tree Shaking、Hermes 优化、移除未使用依赖
Native Init 原生容器初始化耗时 减少 Native Modules 数量、延迟注册

新架构启动优化：TurboModules 支持懒加载——旧架构在启动时就初始化所有 Native Modules，新架构只在首次 require 时才初始化，显著减少启动时间。Fabric 渲染器也支持并发渲染，避免阻塞主线程。

3. 线程安全：多线程如何协作

React Native 有 JS、Shadow、Native（UI）三个线程，但几乎不使用锁。它的安全策略是：通过架构设计，让每个线程只操作自己"拥有"的数据，尽量避免共享可变状态。

各线程的"领地"

线程读写同步机制
JS Thread JS 堆、JSI HostObjects JS 堆、Virtual DOM 单线程，天然串行
Shadow Thread WIP Shadow Tree WIP Shadow Tree（Yoga 布局） 与 UI 线程通过 commit 隔离
UI Thread Committed Shadow Tree（只读） 原生 View 树 MainQueue 串行

策略 1：JS 单线程 — 天然无竞争

Hermes / JavaScriptCore 运行在一个专用线程上，所有 JS 代码串行执行。不存在两个 JS 任务同时修改同一个变量的情况。

// 以下代码在 JS 线程上天然安全，无需任何同步
let count = 0;
function increment() {
  count++;        // 永远不会有并发竞争
  console.log(count);
}
但 JSI HostFunction 是在哪个线程执行的？ 当 JS 通过 JSI 调用 C++ 函数时，C++ 代码运行在 JS 线程上。所以你的 drawCircle() 是在 JS 线程同步执行的，不会与其他 JS 代码并发。

策略 2：消息拷贝 — 不共享可变数据

线程间传递的数据是拷贝，不是共享引用：

┌─────────────────────────────────────────────────────────────────────┐ │ Data Transfer Between Threads │ │ │ │ Old Architecture (Bridge): │ │ ┌─────────┐ JSON 拷贝 ┌──────────┐ JSON 拷贝 ┌────────┐ │ │ │ JS │ ─────────────▶ │ Queue │ ────────────▶ │ Native │ │ │ │ Thread │ │ (Buffer) │ │ Thread │ │ │ └─────────┘ └──────────┘ └────────┘ │ │ 原始对象留在 JS 堆，序列化后副本传给 Native │ │ │ │ New Architecture (JSI + Fabric): │ │ ┌─────────┐ 共享不可变引用 ┌──────────┐ │ │ │ JS │ ─────────────────▶ │ UI │ │ │ │ Thread │ Shadow Tree │ Thread │ │ │ └─────────┘ commit 后只读 └──────────┘ │ │ 无锁：写操作在 Shadow 线程完成，UI 线程只读已提交的快照 │ └─────────────────────────────────────────────────────────────────────┘

策略 3：Fabric 双缓冲 — 核心安全机制

新架构的 Fabric 渲染器使用双缓冲（Double Buffering）来协调 Shadow 线程和 UI 线程：

┌─────────────────────────────────────────────────────────────────────┐ │ Fabric Double Buffering │ │ │ │ Shadow Thread (写) UI Thread (读) │ │ ┌─────────────────┐ ┌─────────────────┐ │ │ │ Work-In-Progress│ │ Committed │ │ │ │ Shadow Tree │ │ Shadow Tree │ │ │ │ (可读可写) │ │ (只读快照) │ │ │ └────────┬────────┘ └────────┬────────┘ │ │ │ │ │ │ │ ┌─────────────┐ │ │ │ └────▶│ Commit │◀──────┘ │ │ │ (原子交换) │ │ │ └─────────────┘ │ │ │ │ 时序： │ │ 1. Shadow 线程在 WIP 树上计算布局（UI 线程不碰这棵树） │ │ 2. 布局完成后，commit：WIP ↔ Committed 原子交换 │ │ 3. UI 线程读取新的 Committed 树，更新原生 View │ │ 4. 旧的 Committed 树（现在是 WIP）被回收或复用 │ │ │ │ 关键：两个线程从不同时写同一棵树 │ └─────────────────────────────────────────────────────────────────────┘

为什么不需要锁？

  • 写写不冲突：同一时刻只有一个线程在写（Shadow 线程写 WIP，UI 线程写原生 View）
  • 读写不冲突：UI 线程读的是已提交的不可变快照，Shadow 线程写的是另一棵树
  • Commit 是原子操作：交换指针（或版本号），瞬间完成，无需锁

策略 4：UI 操作串行化 — 天然队列

所有原生 UI 操作都 dispatch 到主线程的串行队列：

// iOS — 所有 UI 操作 dispatch 到 MainQueue
dispatch_async(dispatch_get_main_queue(), ^{
    // 创建/更新 UIView，在主线程串行执行
    view.frame = CGRectMake(x, y, width, height);
});

// Android — 所有 UI 操作 post 到主线程
UiThreadUtil.runOnUiThread(() -> {
    view.layout(x, y, x + width, y + height);
});

MainQueue / MainLooper 本身就是串行的，不存在并发访问原生 View 的情况。

策略 5：TurboModules — 同步直调但仍在 JS 线程

TurboModules 虽然通过 JSI 实现了同步调用，但调用仍然发生在 JS 线程：

// JS 调用 TurboModule
const result = TurboModule.getData();  // 同步，在 JS 线程执行

// TurboModule 内部的 C++ 代码
// → 也运行在 JS 线程
// → 不需要与 JS 竞争
// → 但如果访问 Native UI，需要 dispatch 到主线程
注意：如果 TurboModule 的 C++ 代码需要访问 UI 线程的数据（比如读取 View 状态），你必须自己保证线程安全。框架不会帮你做这件事。常见做法是 dispatch_async 到主线程，或使用线程安全的数据结构。

哪里真的用到了锁？

虽然架构层面尽量避免锁，但仍有少量必要场景：

锁用途保护什么
jsi::Runtime 安装锁 安装 JSI 绑定时 防止多个 Native Module 同时注册全局函数
JavaScriptContextHolder Android 传递 Runtime 指针时 确保 Runtime 已初始化后才可访问
EventEmitter 锁 Native → JS 事件派发 保护事件队列的并发写入
Shadow Tree commit 锁 Fabric 提交布局结果时 保护指针交换的原子性（通常是 spinlock）

总结：为什么不用传统锁

┌─────────────────────────────────────────────────────────────────────┐ │ Thread Safety Strategy Summary │ │ │ │ 传统多线程： 多线程共享可变数据 → 需要锁 → 死锁/性能下降 │ │ │ │ React Native： │ │ │ │ ✓ JS 单线程 → 消除 JS 层并发 │ │ ✓ 消息拷贝 → 消除跨线程共享可变数据 │ │ ✓ 双缓冲快照 → 读写分离，无锁 │ │ ✓ UI 队列串行化 → 消除原生 View 并发访问 │ │ ✓ 少量自旋锁 → 仅用于 commit 和初始化等边界场景 │ │ │ │ 哲学：不靠锁保护共享状态，靠架构设计消灭共享状态 │ └─────────────────────────────────────────────────────────────────────┘
代价：这种设计的代价是数据新鲜度——UI 线程看到的 Shadow Tree 永远是上一帧的快照，不是实时的。这就是为什么 React Native 的 UI 更新天然有一帧延迟。对于动画等场景，需要用 requestAnimationFrame 或原生驱动的动画（useAnimatedStyle）来绕过这个限制。

5. 架构演进：Bridge → JSI

旧架构：Bridge（已废弃）

JS → JSON 序列化 Bridge Queue → JSON 反序列化 Native

问题：异步、有序列化开销、类型不安全、桥接成为性能瓶颈。

新架构：JSI（推荐）

JS → C++ 直调 JSI Runtime → 同步执行 C++ 实现

优势：同步、零拷贝、类型安全、无序列化。

┌─────────────────────────────────────────────────────────────────────┐ │ JSI Architecture (New) │ │ │ │ ┌──────────┐ ┌──────────────┐ ┌──────────────────────────┐ │ │ │ JS │────▶│ JSI Runtime │────▶│ C++ HostObject/Function │ │ │ │ (Hermes) │◀────│ (C++ ABI) │◀────│ (你的插件代码) │ │ │ └──────────┘ └──────────────┘ └──────────────────────────┘ │ │ │ │ 无 Bridge、无 JSON 序列化、同步调用、零拷贝 │ └─────────────────────────────────────────────────────────────────────┘

6. 本项目实现：TurboModule 版 Circle Plugin

为什么用 TurboModule 而非 JSI 全局函数？
旧方案通过 globalThis.__drawCircle 在启动时注册全局函数，和旧 Bridge 一样是全局注册，没有懒加载。
TurboModule 通过 TurboModuleRegistry.getEnforcing('CirclePlugin') 按名访问，JS 首次调用时才初始化——底层同样是 JSI 同步调用，但模块发现和加载由 RN 框架统一管理。

CirclePluginTurboModule.cpp — TurboModule 实现

#include "CirclePluginTurboModule.h"
using namespace facebook;

namespace circleplugin {

/**
 * HostObject — JS 通过 TurboModuleRegistry 访问。
 * 方法在首次访问时才创建（懒解析）。
 */
class CirclePluginModule : public jsi::HostObject {
public:
  jsi::Value get(jsi::Runtime &rt, const jsi::PropNameID &name) override {
    if (name.utf8(rt) == "drawCircle") {
      return jsi::Function::createFromHostFunction(rt, name, 2,
          [](jsi::Runtime &runtime, const jsi::Value &,
             const jsi::Value *args, size_t count) -> jsi::Value {
            auto result = drawCircle(
                static_cast<int>(args[0].asNumber()),
                static_cast<uint32_t>(args[1].asNumber()));
            auto buffer = jsi::ArrayBuffer(runtime,
                std::make_shared<RawBuffer>(std::move(result.pixels)));
            auto obj = jsi::Object(runtime);
            obj.setProperty(rt, "width", result.width);
            obj.setProperty(rt, "height", result.height);
            obj.setProperty(rt, "buffer", std::move(buffer));
            return obj;
          });
    }
    return jsi::Value::undefined();
  }

  std::vector<jsi::PropNameID> getPropertyNames(jsi::Runtime &rt) override {
    std::vector<jsi::PropNameID> names;
    names.push_back(jsi::PropNameID::forAscii(rt, "drawCircle"));
    return names;
  }
};

/**
 * 包装 __turboModuleProxy，注入 CirclePlugin。
 * 调用时机：JSIModulePackage.getJSIModules()。
 */
void installCirclePluginTurboModule(jsi::Runtime &runtime) {
  auto originalProxy = std::make_shared<jsi::Value>(
      runtime.global().getProperty(runtime, "__turboModuleProxy"));
  auto module = std::make_shared<CirclePluginModule>();

  auto wrapper = jsi::Function::createFromHostFunction(runtime,
      jsi::PropNameID::forAscii(runtime, "__turboModuleProxy"), 1,
      [originalProxy, module](jsi::Runtime &rt, const jsi::Value &,
          const jsi::Value *args, size_t count) -> jsi::Value {
        std::string name = args[0].getString(rt).utf8(rt);
        if (name == "CirclePlugin") {
          return jsi::Object::createFromHostObject(rt, module);
        }
        return originalProxy->asObject(rt).asFunction(rt).call(rt, args, count);
      });

  runtime.global().setProperty(runtime, "__turboModuleProxy", std::move(wrapper));
}

}
TurboModule 核心 API：
• jsi::HostObject — JS 对象的 C++ 代理，get() 在属性访问时延迟调用
• 包装 __turboModuleProxy — 注入自定义模块到 RN 的 TurboModule 系统
• jsi::Object::createFromHostObject() — 将 HostObject 包装为 JS 对象
• shared_ptr<jsi::Value> — 包装 move-only 的 Value，使 lambda 可拷贝

11. Expo Modules 推荐

Expo Modules 是目前最省事的方案：用 Swift/Kotlin 写模块，自动生成 JSI 绑定。

特点

  • 不需要手写 JNI / ObjC++ 桥接
  • 不需要手写 JSI 绑定
  • 用 Swift（iOS）/ Kotlin（Android）写原生代码
  • 自动生成 TypeScript 类型

示例

// Swift — iOS
import ExpoModulesCore

public class CircleModule: Module {
  public func definition() -> ModuleDefinition {
    Name("CirclePlugin")

    AsyncFunction("drawCircle") { (radius: Int, color: Double) -> [String: Any] in
      let result = drawCircle(radius: radius, color: UInt32(color))
      return [
        "width": result.width,
        "height": result.height,
        "data": Data(result.pixels).base64EncodedString()
      ]
    }
  }
}
// Kotlin — Android
import expo.modules.kotlin.modules.Module
import expo.modules.kotlin.modules.ModuleDefinition

class CircleModule : Module() {
  override fun definition() = ModuleDefinition {
    Name("CirclePlugin")

    AsyncFunction("drawCircle") { radius: Int, color: Double ->
      val result = drawCircle(radius, color.toUInt())
      mapOf(
        "width" to result.width,
        "height" to result.height,
        "data" to Base64.encodeToString(result.pixels, Base64.NO_WRAP)
      )
    }
  }
}
// TypeScript — 直接用，类型自动生成
import { requireNativeModule } from 'expo-modules-core'
const CirclePlugin = requireNativeModule('CirclePlugin')

const result = await CirclePlugin.drawCircle(100, 0xFF0000FF)
C++ 代码怎么用？ Expo Modules 支持 expo-modules-core 的 C++ 扩展，或者通过 expo-cpp 桥接。对于纯 C++ 库，可以在 Swift/Kotlin 层调用 C++（iOS 通过 ObjC++ 桥接，Android 通过 JNI）。

12. Nitro Modules Experimental

Nitro 是 Marc Rousavy（react-native-maps 作者）开发的下一代模块框架，基于 JSI + Codegen。

特点

  • 用 TypeScript 定义接口，自动生成 C++ / Swift / Kotlin 绑定
  • 比 Expo Modules 更底层，支持直接操作 C++ 对象
  • HybridObject 模式：JS 对象直接持有 C++ 对象引用

示例

// 1. TypeScript 定义 spec
// nitrogen.ts
import { HybridObject } from 'react-native-nitro-modules'

interface CircleSpec extends HybridObject {
  drawCircle(radius: number, color: number): ArrayBuffer
}
// 2. 运行 codegen，自动生成 C++ 绑定
$ npx nitro-codegen --platform ios android

// 生成:
//   HybridCircleSpec.hpp     ← C++ 抽象接口
//   HybridCircleSpec.cpp     ← JSI 绑定
//   HybridCircleSpec.swift   ← iOS 桥接
//   HybridCircleSpec.kt      ← Android 桥接
// 3. 实现 C++ 接口
class HybridCircle : public HybridCircleSpec {
public:
  jsi::ArrayBuffer drawCircle(double radius, double color) override {
    auto result = circleplugin::drawCircle((int)radius, (uint32_t)color);
    // 返回 ArrayBuffer，Nitro 自动处理内存管理
    return ArrayBufferWrapper(result.pixels);
  }
};
// 4. JS 侧使用
import { getNitroModule } from 'react-native-nitro-modules'

const circle = getNitroModule<CircleSpec>('Circle')
const buffer = circle.drawCircle(100, 0xFF0000FF)
Nitro vs Expo Modules：
• Nitro 更底层，适合需要直接操作 C++ 对象的场景
• Expo Modules 更高层，适合大部分业务模块
• Nitro 的 HybridObject 允许 JS 持有 C++ 对象生命周期
• Expo Modules 适合从 ObjC++/Java 迁移的项目

13. 什么时候该用 C++？

场景建议
简单逻辑（画个圆、字符串处理）Java / Swift 直接写，不需要 C++
已有 C++ 库（OpenCV、FFmpeg、SQLite）用 C++，避免重写
跨平台共享代码（iOS + Android + 桌面）用 C++，一份代码多端复用
性能密集型（音视频、物理模拟、ML）用 C++，性能优势明显
想绕开 JNI / ObjC++ 复杂度Expo Modules 或 Nitro
