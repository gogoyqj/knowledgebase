format_list_numbered How to Approach a System Design Problem

Follow this 4-step framework to tackle any system design question in interviews or real-world projects.

1
Outline Use Cases, Constraints & Assumptions
  • Who will use it? How many users?
  • What are the core use cases? (e.g., post tweet, view timeline, search)
  • What traffic volume do we expect? (requests/sec)
  • Read-heavy vs write-heavy?
  • What's the ratio of reads to writes?
  • What's the expected data size? (GB, TB, PB)
  • What latency is acceptable for users?

Tip: Drive the conversation. Ask questions. Don't assume.

2
Create a High-Level Design
  • Sketch the major components and how they connect
  • Identify the right building blocks: load balancer, API gateway, web servers, databases, caches, queues
  • Define the data flow: client → load balancer → app server → database
  • Get buy-in on the approach before diving deeper
Client arrow_forward DNS arrow_forward Load Balancer arrow_forward Web Servers arrow_forward App Servers arrow_forward Database
3
Design Core Components
  • Dive into each component in detail
  • Define APIs and endpoints (REST, GraphQL)
  • Choose database schema and data models
  • Determine data partitioning strategy (sharding)
  • Design caching strategy (what to cache, TTL, eviction policy)
  • Identify appropriate algorithms and data structures
4
Scale the Design
  • Identify and resolve bottlenecks
  • Horizontal scaling: add more servers behind load balancer
  • Vertical scaling: increase resources on existing servers
  • Add redundancy: replicate databases, use multiple availability zones
  • Use CDN for static content
  • Implement monitoring, logging, and alerting

trending_up Scalability

Scalability is the ability of a system to handle increased load by adding resources.

arrow_upward Vertical Scaling (Scale Up)

  • Add more power (CPU, RAM) to existing machine
  • Simple, no code changes needed
  • Hardware limit (can't scale infinitely)
  • Single point of failure
  • Good for early stage or databases

swap_horiz Horizontal Scaling (Scale Out)

  • Add more machines to the pool
  • More complex, requires load balancing
  • Virtually unlimited scaling
  • Better fault tolerance & redundancy
  • Preferred for large-scale systems

CAP Theorem

In a distributed system, you can only guarantee two out of three:

check_circle Consistency

All nodes see the same data at the same time. Every read receives the most recent write.

check_circle Availability

Every request gets a response (success or failure). No timeout or error.

check_circle Partition Tolerance

System continues to operate despite network partitions between nodes.

Reality: Network partitions will happen. You must choose between CP (Consistency + Partition Tolerance, e.g., HBase, MongoDB) or AP (Availability + Partition Tolerance, e.g., Cassandra, DynamoDB).

dns Domain Name System (DNS)

DNS translates domain names (e.g., example.com) to IP addresses. It's a hierarchical, distributed naming system.

Browser arrow_forward DNS Resolver arrow_forward Root DNS arrow_forward TLD DNS arrow_forward Authoritative DNS arrow_forward IP Address
  • check Results are cached at multiple levels (browser, OS, resolver)
  • check Use Route 53, Cloudflare, or similar managed DNS services
  • check Can route traffic based on latency, geography, or health checks

public Content Delivery Network (CDN)

A globally distributed network of proxy servers that caches content closer to users, reducing latency.

Push CDN

You push content to the CDN. Good for static assets with low traffic. You control what's cached.

Pull CDN

CDN pulls from your origin on first request. Good for high traffic sites. Automatic caching.

  • check Cache static assets: images, videos, CSS, JavaScript
  • check Set appropriate Cache-Control headers and TTL
  • check CDN needs to be invalidated when content changes
  • check Services: CloudFront, Cloudflare, Akamai, Fastly

balance Load Balancer

Distributes incoming traffic across multiple servers to ensure no single server is overwhelmed.

Layer Approach Use Case
Layer 4 Routes based on IP + Port Simple, fast, low overhead
Layer 7 Inspects HTTP headers/content Smart routing, URL-based, A/B testing

Algorithms

  • looks_one Round Robin — Requests distributed sequentially
  • fitness_center Least Connections — Sent to server with fewest active connections
  • memory Least Response Time — Sent to fastest responding server
  • vpn_key IP Hash — Client IP determines which server (session affinity)

Tip: Use active-passive or active-active load balancers to eliminate single point of failure.

swap_horiz Reverse Proxy (Web Server)

Sits between clients and servers, forwarding client requests to the appropriate backend server.

check Benefits

  • Increased security — hides backend servers
  • SSL termination
  • Caching static content
  • Compression (gzip)
  • Built-in rate limiting

compare vs Load Balancer

  • Reverse proxy: single server focus
  • Load balancer: multiple servers focus
  • Often combined in modern setups
  • Nginx, HAProxy, Apache, Caddy

developer_board Application Layer

Separating web and application layers allows them to scale independently.

Microservices

Break application into small, independent services. Each owns its data and logic. Deploy independently.

Service Discovery

Services find each other via service registry (Consul, etcd, ZooKeeper). Enables dynamic scaling.

Trade-off: Microservices add complexity (network calls, data consistency, debugging). Start with a monolith, extract services when needed.

Scaling Techniques

content_copy Replication

Master-slave: One write, many reads. Master-master: Writes to multiple nodes. Provides redundancy and read scaling.

grid_on Sharding (Partitioning)

Split data across multiple databases. Each shard holds a subset. Hash-based or range-based partitioning.

account_tree

Master-Slave Replication

Master (writes) → Slave 1, Slave 2, Slave 3 (reads)

cached Cache

Caching stores frequently accessed data in fast storage (RAM) to reduce database load and latency.

Client-Side

Browser cache, HTTP cache headers. Fastest, but limited control.

CDN

Edge caching for static assets. Geographically distributed.

Application-Level

Redis, Memcached. In-memory key-value stores. Microsecond latency.

Database

Query cache, buffer pool. Built into the database engine.

Caching Strategies

Strategy Description When to Use
Cache-Aside App checks cache first, then DB General purpose, read-heavy
Write-Through Write to cache and DB simultaneously Need consistency, write-heavy
Write-Behind Write to cache, async write to DB High write throughput, eventual consistency OK
Read-Through Cache handles DB reads transparently Simplified app code

Eviction Policies

  • access_time LRU (Least Recently Used) — Evict least recently accessed item
  • schedule LFU (Least Frequently Used) — Evict least frequently accessed item
  • timer TTL (Time To Live) — Evict after expiration time
  • casino FIFO (First In First Out) — Evict oldest item

queue Asynchronism & Queues

Async workflows prevent slow operations from blocking the user experience.

message Message Queues

Producers send messages to a queue. Consumers process them independently. Examples: RabbitMQ, Amazon SQS, Kafka.

task Task Queues

Workers pull tasks from a queue and execute them. Examples: Celery, Sidekiq, AWS Lambda.

User Request arrow_forward Server arrow_forward Queue arrow_forward Worker arrow_forward Database

Use cases: Send emails, process images, generate reports, update search indexes — anything that doesn't need immediate response.

RPC vs REST

code RPC

  • Action-oriented (verbs)
  • Tightly coupled
  • Fast, efficient (binary protocols)
  • Good for internal microservices

api REST

  • Resource-oriented (nouns)
  • Loosely coupled
  • Human-readable (JSON/HTTP)
  • Good for public APIs

security Security

  • lock HTTPS everywhere — Encrypt data in transit with TLS/SSL
  • vpn_key Authentication — OAuth 2.0, JWT tokens, OpenID Connect
  • admin_panel_settings Authorization — Role-based (RBAC) or attribute-based (ABAC) access control
  • shield Input validation — Prevent SQL injection, XSS, CSRF attacks
  • policy Rate limiting — Prevent abuse and DDoS attacks
  • key Secrets management — HashiCorp Vault, AWS Secrets Manager
